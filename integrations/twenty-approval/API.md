# 审核后台适配约定（v1）

供 Codex 实施时使用，客户只决定业务规则。本包实现调用方和 Twenty 页面；以下持久化、权限、规则与执行逻辑由客户后台提供。不要把旧作者 API 地址填入应用；旧 `/v1/p3/approval-requests` 格式与本接口不兼容，需要适配。

## 路由与身份

应用服务端携带 `Authorization: Bearer <客户 Token>`、`x-cra-workspace-id`、`x-cra-reviewer-id`。审核人取自 Twenty 登录会话的 `workspaceMemberId`；浏览器不能指定审核人、工作区或业务动作。后台必须校验 Token 绑定的工作区及可信代理来源，再校验成员对该规则/记录的权限；请求头本身不是权限证明。拒绝任意工作区切换或直接从公网伪造身份。

| 请求 | 返回 |
|---|---|
| GET `/v1/review/requests?status=pending&limit=50&cursor=…` | `{ values: ReviewRequest[], nextCursor: string或null }` |
| POST `/v1/review/requests/{id}/decision` | `{ value: ReviewRequest }` |

列表只返回当前审核人允许查看的记录，按创建时间和 ID 稳定分页，最多 50 条/页，不因只返回前 50 条隐藏后续事项。状态支持 `pending/approved/rejected/superseded`。决定请求字段为 `id, planDigest, outcome, note, selectedChoiceId`；id 必须与路径一致，outcome 只允许 approved/rejected，note 最长 4000 字符。无候选或拒绝时 selectedChoiceId 为 null。

记录形状以 [contracts.ts](src/lib/contracts.ts) 为准。`id`、选项 ID 和工作区使用字母/数字/下划线/连字符；`planDigest` 为 64 位小写 SHA-256；时间为带时区 ISO 8601。显示内容均为普通文本，不传 HTML。`changes` 的 before/after 使用客户可理解的文本和单位，空字符串分别表示未填写/清空；创建、删除、改归属也应有清楚的动作摘要。`choices` 为空时直接通过/拒绝，非空时通过必须选一项。证据引用定位原文，不能伪造证据；无消息来源的人工提案可引用其业务记录或操作来源。

返回必须包含工作区、规则 ID 和版本、准确状态及 `canDecide`。approved/rejected 有对应决定（审核人显示名、时间、备注、选择），且 canDecide 为 false。pending 尚无决定，拒绝和待审的执行状态必须为 not_started。不得把未配置后台当作空列表返回。

## 规则到待审核

客户完成业务问答后，在既有后台配置采用的 `auto/review/manual/read_only` 语义或等价策略。所有**拟变更且需要人工决定**的分支，无论来自模型、身份匹配、冲突保护或业务工作流，都落入同一持久审核队列；普通日志不算客户可处理入口。纯手工维护字段只有产生待确认提案时才生成审核项，无提案不凭空催审。网络暂时失败走有界重试；AI 分析最多尝试 3 次（含首次），耗尽或判定不可重试的终止错误须在统一待审核页的独立“系统处理异常”区可见，不进入业务决定队列。

系统异常按未解决任务身份去重，提供影响范围、状态、尝试次数、脱敏错误码和任务/日志定位，供客户交给 Codex 或维护人员处理；无字段提案不伪造 changes，也不强制通过/拒绝。失败可直接从持久状态读取或可靠投递，不能依赖模型成功产出审核提案。恢复成功后退出当前异常列表，原失败和次数保留；读取故障不得当作零异常。

**v1 的上述两个路由与随包源码尚不提供独立异常列表/通知。** 部署时在客户副本增加相应受保护的状态查询和页面区域，沿用服务端工作区/成员校验；状态区与业务队列分别计数，不能仅将失败拼成 ReviewRequest。字段至少能表达稳定异常 ID、影响范围、处理环节、状态、尝试/重试信息、脱敏错误与定位；分页/总数和读取失败语义明确。技术恢复如需要界面动作，应单独绑定精确任务与权限；不得经业务 decision 端点批准空提案来触发。

修复后在已授权的具体范围内创建关联原任务的有界恢复任务（仍最多尝试 3 次），保留旧次数和错误，新分析结果仍按正常字段策略判断。仅恢复通知投递不重调模型。具体布局、交接和提醒边界见 [实施要求](../../references/13-review-app.md)。

一条审核记录关联：不可变动作/字段前后值、真实对象/记录映射、证据、规则版本、预期目标版本、候选集合、幂等键及可用执行方式。展示类型不限制业务类型；通用页面支持不代表后台已实现某动作，未支持的动作需明确标为待实现或批准后人工完成，不能静默放行。

## 保存决定与执行

1. 事务内锁定或比较并交换当前审核版本，校验成员权限、工作区、pending 状态、摘要、选择和当前规则是否仍允许；不能依赖应用的读取后写入代替原子校验。
2. 同一决定重放返回首次决定，不改变最初审核人/时间，不再次入队；相反决定、过期计划、已失效请求、选择不在候选中返回 409。权限不符返回 403。
3. 批准将被审核的精确计划与选项通过事务或可恢复的幂等衔接交给既有执行器，拒绝不执行。字段变更不得重新调用模型生成另一份计划并沿用批准；技术分析恢复不使用此业务决定端点。后台重启也不能丢掉已批准待处理的事项。
4. 执行前重新核验真实对象、字段与目标版本。期间被人工修改、规则收紧或映射变化时阻断旧任务，旧请求保留历史并失效；需再次决定的变更生成新审核项，不能只留在错误日志。
5. 执行成功并回读后才能返回 `execution.status=succeeded`。queued/running/conflict/failed 分别表示等待、执行中、冲突和失败；只保存批准不能算成功。需要人工在 CRM 完成的操作用 manual_required，message 给出负责人和具体步骤，核实实际结果后再改成功。

审核不需要等下一次每日模型分析才能继续。后台按自己的执行调度处理批准与恢复；已有字段计划无需再次分析消息。技术故障在授权范围内恢复时仅重新处理指定的失败范围，不重跑已成功步骤，不把新分析结果冒充此前获批的字段计划。查看历史审核时同步提供当前执行结果，保持批准时间与执行时间可追溯。

## 接入验收

以客户每条已确认审核规则的正反例验证：应审核的进入待审核且写入前停止，普通自动更新正常执行；通过、拒绝、候选选择、无权限成员、跨工作区、旧摘要、并发人工改动、重复提交、超时后的回读、恢复及分页。验证真实 Twenty 登录会话与后台身份传递、记录版本和 CRM 回读。应用单元测试只验证调用边界，不替代后台事务和真实闭环。
