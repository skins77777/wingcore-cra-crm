# 将企业业务规则落实到模型与 CRM

在已有 crm-fde 或等价业务档案、需要生成提取规则或配置模型时读取。业务答案保存在同一份客户档案，不另外发明一套企业规则。

## 先按流程收拢每一步变更规则

生成涉及商机阶段的提取配置前，读取 [逐阶段成立与识别条件](10-stage-rules.md)，按企业流程顺序逐步收拢“当前阶段 → 下一阶段”的变化条件、可接受证据、相关客户/商机字段动作及人工确认方式；当前一步未收拢，先补该步骤缺口。不能把阶段名称、全流程预备草稿或单项条件的确认当成已完成所有变更规则。首次承接从流程入口开始，每一步结合授权聊天、邮件、客户档案与本商机上下文，展示原定义、建议及考量，听取客户保留或修订的答复；原答案完整也不跳过，续接时则引用本轮已复核决定；阶段名和流程图不能替代证据，“确认”字样也不构成额外人工回复或审批条件。明确采用人工维护的阶段不启用 AI 自动变更；待定阶段保留不变，已就绪的其他规则可继续实施。

## 从档案生成提取说明

逐项读取已采用的字段、阶段条件、数据来源与唯一维护者。将实际需要 AI 理解的内容整理为下表，保存在客户现有字段字典或其引用的提取说明中。将本轮复核后的业务语义写给模型，不把初次访谈答案或尚未获采纳的建议当作最终规则；内部名、字段类型、模型接口和部署路径由 Codex 核实。

| 内容 | 从哪里来 | 给模型/程序什么信息 |
|---|---|---|
| 业务事实 | 字段定义、阶段条件、客户决定 | 含义、成立证据、否定/意向/更正的区别 |
| 目标对象 | 客户/联系人/商机关系和已核实映射 | 当前可选择的记录、歧义时不猜 |
| 输出字段 | 字段字典和更新归属 | 允许输出的字段、类型、单位、枚举及未知表示 |
| 写入条件 | 已确认自动化边界 | 自动执行、例外处理、仅供参考及人工保护 |
| 下游动作 | Twenty 工作流及其他运行组件 | 唯一执行者，避免重复建单、评级或提醒 |
| 案例 | 客户确认的业务正例和反例 | 预期事实、应变更字段及不应改变内容 |

能从已确认答案推导的提取说明由 Codex 整理，不要求客户手写提示词。比如客户确认“合同签订算赢单”，模型需要区分“已签署”和“准备签署”；程序如何更新阶段依照真实映射。是否允许自动推进、何时建单仍沿用企业决定，不添加通用审批要求。

## 业务答案怎样写给模型

按流程逐步确认变更规则，并随各步骤收拢相关 [字段规则](11-field-rules.md) 后，整理为人能读懂的识别说明，再转换为实际组件接受的格式。至少包含：

- 企业采用的对象和字段含义，客户长期关系与单笔采购的区别。
- 每阶段所需事实、条件组合、可接受来源和不成立例；字段首次赋值、更正、未知与冲突策略。
- 新采购/原单变化的判断，相关客户资料、当前商机字段和历史事实如何补充本次信息。
- 输出需要的事实、值、对象引用和证据；不确定可保持不变。提示、输出校验器和运行程序对证据格式保持一致。

比如已确认“订单总价只在客户明确接受后写入”：提示应解释未接受报价、明确总价、计划定金和退款的区别，要求保存金额原文及币种。程序检查成立条件并编码到真实金额字段。具体示例见 [连续示范](12-worked-example.md)。

借用现有程序时检查它支持的是语义事实还是直接字段候选：事实型需要把事件及条件组合映射到动作；字段候选型仍要验证允许的对象、字段和业务前提。不能只更换阶段名称而忽略程序中写死的旧条件。

运行时给模型的输入由实际来源构成：完整新增信息、适用客户资料、商机目录或本商机状态、滚动记忆及必要原文。数据库里有资料不代表已经放入模型上下文；逐项核对实际载荷，跨渠道尚未合并时不得声称已综合判断。

## 生成一套相互一致的配置

先读所选运行程序实际接受的格式，再生成：

1. 模型指令：企业规则、逐阶段成立与不成立条件、可接受的说话方/证据、所需上下文、允许的变更、不确定时的处理；复用已确认正反例，不把行业例子当默认规则。
2. 输出结构：运行程序支持的事实或字段候选结构，带记录引用、字段/事实标识、值、证据引用和未决原因。程序只接受允许的字段及类型。
3. 映射和执行配置：业务标识对应 Twenty 内部字段、枚举、关系；字段由 AI、人工或原生工作流维护；允许的阶段转换、更新字段和自动操作。涉及重报价、跳转或回退时使用客户已确定的动作与当前状态条件，不能只改提示词。

模型可输出有依据的字段变更建议，运行程序负责验证并按企业策略执行；不要把“模型不能直接持有 CRM 写入权限”误解成“所有更新必须人工批准”。统计与确定性计算交给已有程序或 Twenty，模型提供需要理解的原始事实。

三者保存相同业务版本及实际运行版本，旧任务重试不能被新提示重新解释。提示词更新后确认后台真正加载了它；只写文件不算生效。`handoff.json` 是可选的结构检查格式，不是运行程序统一配置或必填审批表。

## 输单规则的模型与程序分工

读取crm-fde已确认的失败/不回复/停滞条件及已有Twenty期限工作流，按 [输单与停滞](10-stage-rules.md) 完成本轮复核。保留未改变的确定性流程，模型配置只补它需要理解的事实；改变规则时同步修改原工作流，不重复实现计时关单。模型识别有效回复、采购进展、失败表达和对应对象，输出原文证据及允许的主要原因选项；Twenty工作流或同版档案指定的唯一计时执行者计算期限、适用阶段及重置，不能把模型猜测的沉默时长当计时依据。读取缺口不等于客户没回复。

从crm-fde同版字段字典加载原因枚举和映射；阶段与原因一起校验写入，难归类用其他及说明，不临时增加自由文本类别。验证新回复到达与定时关闭的先后、跨渠道有效回复、历史明确原因不被通用超时原因覆盖，以及转输单后保留客户与其他商机。

## 分析调度配置

按 [每日批量分析规则](04-analysis.md) 配置一天一个常规批次，执行时刻和时区读取客户决定。模型调用入口由批次驱动，消息 Webhook 只接收保存；不要因平台支持实时触发就逐消息调用模型。记录实际调度配置、批次去重、增量边界、分组和失败补跑策略，并回读确认运行组件已加载。只修改提示词不能改变后台调用频率。

同时落实同一 AI 分析任务最多尝试 3 次（含首次）、跨重启持久计数、逐次日志和终止错误进入 CRM 待审核；核对 SDK/HTTP/队列是否存在额外隐藏重试。默认不设每日 token 硬上限，已有上限按客户本次确认的策略调整并回读。次数限制和错误投递由后台实现，不能只写进模型提示；真实配置、日志及待审核页面分别验证。

## 接通模型服务

优先使用客户已有模型 API 与实际运行组件。读取该版本官方 API 文档和组件配置入口，确认 endpoint、模型标识、认证、结构化输出能力、超时、上下文限制和预算。不要猜环境变量名或假设所有兼容接口行为相同。

凭据写入该运行环境的 Secret 或受限配置，档案仅保留引用；不把凭据放进提示、模型输入或通用 Skill。通过运行组件的真实模型调用验证，分别记录认证/网络失败、输出格式失败和业务理解错误。启动服务的方法、配置位置、模型版本、日志入口和重启/重载方法写到客户部署记录。

通常“部署大模型”在这里指接通并配置模型 API。客户要求本地模型时再选择推理服务和硬件，不能承诺在 2 核 4 GB 上运行任意模型。没有后台组件时先按 [运行组件](06-runtime.md) 处理，不把 Codex 当前对话当持续运行服务。

## 最小联调与规则修改

对每条本次启用或修改的阶段识别规则，用已确认的成立正例和不成立/证据不足反例验证实际模型输出；涉及金额、同客户多商机或更正时补对应案例。检查原文支持结论、对象匹配和类型编码，再按客户已有授权做测试记录写入及回读。

最后通过真实渠道到后台到 Twenty 的链路验证，另按启用方式验证真实调度。部署记录保存实际命令、版本与结果，不复制凭据和真实聊天到通用包。

客户改规则时，先改同一档案，更新受影响的提示、输出、字段映射或工作流，然后只验证受影响案例。无需重做访谈、重装 CRM、补全通用引擎或设计一个审核界面。
