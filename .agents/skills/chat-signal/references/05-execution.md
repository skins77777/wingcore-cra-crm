# CRM 指令、审核与可靠写入

## 从事实到不可变任务

确认消息属于哪个客户与商机 → 校验规则/字段/证据/人工保护 → 生成精确变更计划 → 按客户策略自动入队或进入例外审核 → 执行并回读。

计划包含逻辑工作区、目标身份、动作、字段前后值、证据、规则/映射版本、远端预期版本和业务幂等键。入队时保存不可变快照，不在重试时重新调用模型或读取新候选改变原请求。不存在可靠映射时不猜字段或 UUID。

## 任务生命周期

| 状态 | 含义 |
| --- | --- |
| preview | 仅生成计划，没有入队 |
| needs_review | 等待具体例外决策 |
| approved | 决定已保存，未必已入队 |
| pending | 已持久化、可按策略执行 |
| leased | 某代执行者已领取，有有限租约 |
| succeeded | 已得到符合约定的执行结果与回读证据 |
| conflict / failed | 需重校验或人工处理，不冒充成功 |

状态名称可以适配现有系统，但语义必须可区分。随包应用分别显示审核决定与执行结果。作者早期 App 只保存决定，后续 VPS 实现已承接部分审核后的执行，删除仍需人工操作；这些历史边界不代表客户环境已具备能力。客户部署必须逐项验证，不沿用“批准等于完成”的表述。

## 审核范围随客户策略

已有明确授权的普通自动更新无需逐条重新批准。匹配歧义要求选择具体候选；删除、跨客户改归属等动作按客户约定及实际权限执行。原项目选择了三类例外（歧义、删除、改归属），是参考策略，不强制所有客户采用。

审核绑定精确计划摘要、目标和证据版本；修改计划后旧批准失效。重复相同决定返回已有结果，相反决定/过期摘要报冲突。决定到任务入队需事务或可恢复的幂等衔接，不能丢单或重复执行。

客户版保留统一待审核入口，所有按企业规则需人决定的拟变更都汇入其中，包括需要人工解决的业务冲突；不能只记 blocked/日志。优先复用客户已有等价入口，否则配置 [随包 Twenty 应用](13-review-app.md)，无需另建独立管理前端。页面使用登录会话调用服务端，外部 Token 仅在服务端保存。目标工作区成员 ID 与全局用户 ID 不混用；名单和权限从客户实际成员解析。服务端验证来源与响应工作区，分别测试允许和不允许的真实成员。

## Outbox 与外部副作用

- 用数据库唯一约束保障工作区+幂等键，同键同内容复用，同键异内容拒绝。
- 领取使用事务/原子更新、租约与递增 generation。执行者过期后回收，旧代不能提交新状态。
- 每次 attempt 保存尝试、结果、错误分类与下次时间。瞬时错误有限退避；类型/权限/业务冲突不盲目无限重试。
- 外部创建优先使用目标支持的固定 ID 或幂等请求；请求超时可能已成功，先按稳定身份回读。远端不支持幂等时保留“不确定结果”核对流程，不能承诺 exactly-once。
- 更新使用目标经过实测的并发保护。单纯先 GET 再 PATCH 不是原子 CAS；不把任意 filter 视为版本约束。
- 任务与成功映射尽量事务保存，但本地事务不能涵盖外部 API。用恢复与对账填补失败窗口。

人工修改之后的旧任务不得无条件覆盖；对单调字段、人工锁定字段和普通字段分别定义合并规则。重试与修正不是同一请求，内容改变需新版本/键。

## Twenty 适配与工作流

每个字段校验对象、类型、内部名、枚举值、金额编码与关联方向。显示标签、枚举内部值、看板排序分别核对。富文本、姓名与金额可能是复合值，不用普通字符串猜写。

明确赢单建单、订单累计、客户等级与阶段的唯一维护方。订单重复保存、金额修正、作废与关联变化应保持统计一致。不能只依赖“查询没有订单再创建”的非原子并发路径。

保留已有公司关联；内置自动建公司流程是否会覆盖关系要验证。首次创建客户/联系人/商机时，处理依赖顺序和中途失败；不能把创建草稿当真实 CRM 记录已存在。

## 若扩展主动发消息

单独定义发送范围、接收人、模板/内容、账号、时机、限速、拒收策略、回执和不确定结果核对。读取聊天的授权不包含发送授权；不存在接入能力时不得伪造已发出。CRM Outbox 的成功状态也不能当作 WhatsApp 送达。
