# 按客户规则配置“待审核”应用

客户完成业务和字段规则后，将需要人决定的拟变更统一接入 Twenty 的“待审核”，同时让客户知道系统处理失败。已有等价入口优先复用。本包附 [业务审核应用源码](../assets/twenty-approval/README.md)；源码的现有能力和本节要求必须逐项比较，不能把指导文档当成已经实现的功能。

## 从同一档案取得规则

沿用共同档案中每条规则的触发条件、反例、目标字段、原值/拟改值、证据、审核成员、选择后的动作与执行状态。阶段名称和人工范围由企业决定，不固定为匹配、删除、改归属三类。明确的信息按已定策略自动写入，暂缓需要人判断的部分；业务审核不应挡住无关的确定性更新。

## 页面布置

按以下结构配置同一个入口，窄屏保持同样的信息顺序：

| 位置 | 内容 | 客户可做的动作 |
|---|---|---|
| 顶部 | “待审核”、简短说明、刷新、最近检查时间/读取状态 | 刷新；理解哪些需要自己决定、哪些需要技术维护 |
| 顶部独立区域 | “系统处理异常 · 数量”；无异常时一行状态，有异常时醒目但紧凑 | 展开受影响客户与排查指引，复制信息给 Codex/维护人员 |
| 主体“需要你确认” | 真正的业务问题卡片及待处理数量 | 选择候选、接受建议、保留原值或拒绝，填写可选备注并提交 |
| “已处理的业务确认” | 原问题、证据、决定人/时间、选择/备注及当前执行状态 | 查看已记录、待执行、成功、失败或因资料变化而失效的结果 |

技术失败数量与业务待确认数量分开。错误读取失败不能冒充“没有异常”；初次加载、空列表、局部失败与刷新中要有明确状态。记录超过一页仍可访问，计数不能只等于当前页条数。

### 业务问题必须能回答

每张卡片包含客户/相关商机、一个具体问题、为什么拿不准、当前值/建议值、支持或冲突的聊天摘录（方向、时间、可追溯引用），以及可提交的处理选项。选择后再提交；重复点击不能产生重复动作。只有日志、原因码或一句“待确认”而无选项，不算可用审核。

- 阶段不确定：展示“是否将此采购从当前阶段改为建议阶段”，说明缺少/矛盾的业务事实；客户可以接受或保留。
- 字段不确定：针对姓名、公司、地址等具体字段提问，确定的其他字段照常处理。
- 商机归属不确定：展示可解释的现有采购候选；符合已定新采购条件时才提供新建选项，也可暂不关联。不能将“谢谢”、问候或单独补城市强制变成商机归属问题。
- 金额未在文字里明确不等于文件审核，纯文字模式保持未知。已知旧信息未被否定时保留，不能因本次没提就要求重新确认。

批准只针对所展示计划、选项和证据版本。提交时已被人工改动或规则变化，应提示原问题失效并按实际新值重新提问，不能覆盖新值。批准、入队和执行成功分别呈现；执行后回读 CRM 才可显示成功。

### 系统处理异常让客户知道影响和找谁

技术异常包括分析失败、额度内待重试、CRM 录入失败和需要技术排查的写入冲突。显示受影响客户/范围、日期、分析或写入环节、状态及下一步；展开后提供任务/批次编号、尝试次数、脱敏错误码和日志定位。未关联客户如实标明，不编造业务记录。

提供“复制排查信息给 Codex”或等价可复制文本；复制不代表已经通知 Codex，也不自动向外部模型发送聊天。排查文本不含密钥、完整原始响应或附件内容，客户不需要理解堆栈。此区域不设置业务通过/拒绝按钮；若产品另有技术恢复操作，应单独命名并绑定准确任务与权限，不能绕过写入校验。

提醒取自当前未解决状态，按任务去重；修复并验证完成后自动退出当前列表，保留运维历史。不得将历史商机归属 exceptions、已解决错误或停用能力的纯附件状态堆在这里。混合阻塞仍保留真正未解决的技术原因，不能为清空列表掩盖故障。采集或调度失败也应通过现有监控接入或标明尚未覆盖的范围，不能宣称仅查询写入队列即可检测全部故障。

## 消息提醒要说明实际作用范围

分别核实目标 Twenty 版本、SDK 与已装应用对以下能力的支持：页面内刷新/弹出提示、侧栏未处理计数/红点、全局消息中心/铃铛、站外通知。核实可用接口与会话行为后实施，不凭菜单名称推断。

页面打开时可按约定间隔自动检查（例如一分钟），新业务问题和技术失败分别提醒，同一事项去重，加载更多不算新事件；查看“已处理”时也应能发现新的待办。查看提示不等于完成事项，解决状态由后端事实决定。离开页面后的全局通知需要独立能力，页面组件卸载后的轮询不能承担它。

参考现场在 Twenty 2.40.0 中未找到可用的通用全局铃铛接口，实际实现仅为待审核页内刷新和弹出提示；这是现场版本的已知边界，不能写成全部 Twenty 版本都不支持，也不能宣称已有全局通知。客户希望全局提醒时，先核实现有能力，再提出当前需求范围内的适配；不擅自发送邮件、WhatsApp 或安装新的通知服务。

## 将规则落实到后台与应用

1. 盘点模型、身份归属、工作流、冲突保护各条路径，将需人判断的拟变更持久化到业务审核队列；技术失败通过独立状态查询/可靠投递进入异常区。失败不能依赖模型成功产出提案后才出现。
2. 同版档案派生触发条件、精确计划、候选、证据、规则版本、执行方式和权限。页面只展示并提交决定，不维护另一套规则。
3. 将随包源码复制到客户项目后适配。配置客户 API、绑定工作区的 Token、工作区 ID 和真实 workspaceMemberId；不照抄作者标识。按 [API 约定](../assets/twenty-approval/API.md) 接通后台；独立异常区及通知能力尚未包含在 v1 源码中，需要在客户副本中补齐并实测。
4. 保存决定与执行器幂等衔接，审核后按后台执行调度继续，无需等待第二天模型分析。无自动执行能力时明确负责人和步骤，不能显示成功。
5. 按锁文件构建、测试、类型检查，核实目标兼容性后用 CLI 非删除式发布。记录应用与后台各自版本，不把安装完成写成闭环完成。

## 验收与交付

对照 [故障回归案例](14-processing-lessons.md) 和 [验收记录](../assets/acceptance.md)：验证业务选项、拒绝/保留、重复决定、计划过期与并发人工修改；也验证技术失败无提案仍可见、旧附件不催审、成功后提醒消失、列表分页、读取失败、复制失败回退、成员/工作区隔离。

通知需实测打开页面、查看历史、离开页面及重新进入的行为，并分别报告哪些范围已实现。不要向真实客户注入假故障来证明提示；先用隔离数据验证，再核对真实列表与状态。真实登录会话中的 UI、后台决定、执行任务、CRM 回读分别留证；HTTP 200、单元测试或保存批准均不能替代完整验收。

客户手册说明“业务问题怎样回答、系统失败怎样交给 Codex、决定后在哪里看执行结果、提醒在什么页面/范围出现”。交付区分规则已确认、应用已安装、后台已接通、页面已验证和生产已启用。
