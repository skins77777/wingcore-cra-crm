# 消息采集、身份与证据

消息接收与分析调度分离：收到消息时完成鉴权、去重和持久保存，不逐条触发模型分析或聊天驱动的 CRM 更新。尚未处理的消息由客户指定时刻的每日批次统一读取；编辑、撤回和断线回补也进入待处理增量，已识别失效的证据须阻止相关旧任务继续执行。

## 账号与来源

将外部实例绑定到逻辑工作区、渠道账号和业务员。凭据解析得到身份，再验证 URL 账号与 payload 实例一致；不能仅信任请求正文中的 workspace。电话号码、WhatsApp JID/LID、联系人及公司是不同标识，按目标版本核对标准化与绑定。

一客户多业务员、同一联系人多个号码、同一联系人多笔采购分别验收。原单账号入口的成功不能证明多账号支持。群聊、历史导入、媒体和消息修订按实际启用能力列范围。

## WhatsApp 与 Email 进入同一信息处理流程

WhatsApp 使用实际接入组件读取入站和出站，保留账号、会话、消息标识、时间、正文及引用关系。不要只采集客户来信而遗漏销售正式报价等行为。Evolution 是参考实现，事件及字段按实际版本核实。

Email 可复用已验证接入或使用 IMAP。按客户授权范围读取收件箱和发件箱；首次历史回溯时长明确记录，之后按文件夹游标增量读取。只读采集不改变已读标记、移动邮件或发送邮件。既有参考实现的 30 天回溯不是所有客户的固定要求。

- 本地解析 MIME、正文与收发地址，登记自有邮箱及别名。普通入站以真实外部发件人为身份依据；出站沿已有回复关联或唯一直接收件人匹配。抄送人不自动建客户，多直接收件人不猜唯一归属。
- 独立站通过自有邮箱转发的询盘，应验证可信转发来源、唯一外部 Reply-To 与正文身份的一致性；普通转发正文里出现一个邮箱不够。
- 系统通知、退信和群发先过滤归档；模型仍需区分漏过过滤的供应商推销与客户采购询盘。陌生地址本身不构成新客户或新商机。
- 邮件本体和文件夹副本分别去重，例如 Message-ID 与文件夹 UIDVALIDITY/UID；持久保存成功后推进游标。缺 Message-ID 时使用经验证的回退标识，不承诺能跨副本去重。
- 回复链用于选择沟通背景，不等同商机。主题、域名相同不自动合并客户或采购；同一回复链可以谈多笔采购。引用邮件超出回溯范围时标明缺失并按需补取，不猜其内容。

合格信息进入统一证据存储和每日分析流程，保留来源、方向、身份、时间和完整性标记。附件元数据不是附件内容，解析能力另行核实。

## 关联已有 CRM 与跨渠道上下文

先按完整电话/邮箱等已核实身份匹配。唯一匹配时读取已有客户、联系人及商机背景，避免重复建档；多个候选保留具体冲突。跨渠道指向同一联系人，也仍要判断每条信息属于哪笔采购。

分别验证“两个渠道都能收”“能关联到同一客户”“模型能在一次业务判断中使用两边证据”“联系人总览能合并且不会相互覆盖”。若后台仍按账号/渠道身份独立分析，明确该限制，不能把共用模型或数据库说成完整融合。需要时做当前客户范围内的上下文适配。

## 接收事务与重放

历史实现的两道业务键可作为设计依据：事件按工作区+账号+外部事件 ID+事件名去重，消息按工作区+账号+外部消息 ID 去重。事件名、实例和 revision 规则依供应商实测，不直接照搬。

将规范化消息与已处理事件在事务中保存；确认持久提交后响应成功。同键同内容返回已有结果，同键异内容记录冲突，不能静默覆盖。比较规范化内容摘要，避免 JSON 键顺序产生假冲突。不要完整记录携带密钥的原始 payload。

至少保存来源账号、会话身份、外部消息 ID、方向/发送者、正文或媒体引用、发生时间、接收时间、修订标识、处理游标。发生时间不可靠时明确标注来源/未知，不把导入时间伪装成业务发生时间。

## 断线与补齐

分开管理连接状态与证据完整性。connected 仅代表当前连接恢复；缺口区间应在历史回补或对账确认后关闭。保存最后成功消息/游标、断线区间、回补状态与失败原因。数据源不能可靠回补时明确记录缺口，不用连接绿灯掩盖。

## 编辑、撤回与引用

对已有消息建立修订链，并让依赖旧版本的事件、候选、小结和未执行任务失效或重新验证。不得删除审计来模拟“从未发生”。已写入 CRM 的变化需要按客户纠错规则判断补偿，不能无条件回退人工后续修改。

供应商事件名称与结构会变化；检查实际版本是否使用 edit、update、delete 或 protocol message。解析器写了分支、Webhook 订阅了事件、实际收到并处理是三个独立验收点。

## 附件与数据范围

客户要求“不识别附件、只分析文字”时，记录为生效的数据范围。模型载荷、覆盖校验和写入门槛均采用同一范围；纯附件增量不调用模型，不建立虚假业务事件，也不误标附件已识别。附件占位、文件名及 MIME 不作为金额/数量的证据。含文字的媒体说明是否纳入由采集器实际可读字段及客户范围决定，不静默丢弃已允许的文字。文字未明确的金额保持未知，不反复催促审核附件。

切换纯文字模式后，排查旧任务中的附件阻塞并做有范围的恢复；不能只隐藏提醒而继续阻断录入。渠道断线、邮件缺页、正文截断、修订失效等真正的文字缺口仍需保留保护。具体回归见 [故障经验](14-processing-lessons.md)。下述附件识别约束仅适用于客户另行启用的附件能力。

保存下载、识别、失败与不适用状态。只拿到文件名或 MIME 不等于读取图片/PDF/语音。OCR/转写是可选适配，需明确存储、访问与生命周期；不要把 `MEDIA_NOT_DOWNLOADED` 标成已完成。

缺附件应阻断依赖它的字段，而非默认永久阻断同一客户所有新文字事实。例如明确的联系人姓名可以更新，报价单金额仍待识别。实施前核实现有引擎能否做到这种粒度。

授权范围落实到账号、成员和查询过滤，不能只在 UI 隐藏记录。模型仅接收该客户/采购必要片段；日志、评估和分发包使用合成或授权脱敏样本。
