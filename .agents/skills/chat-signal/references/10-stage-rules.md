# 沿企业业务流程逐步确认变更规则

在 crm-fde 或等价档案已生成业务流程后使用。业务流程来自该企业的答案，阶段、顺序和变更条件都不是 Skill 的预设。crm-fde 是客户首次理解和描述业务的结果，chat-signal 要带客户第二次走完整流程，通过原定义、建议、理由和新增信息共同完善规则，再据此生成模型说明与执行配置。

## 先确定流程和当前步骤

读取同一份业务档案中的流程、字段与决定，向客户简述所采用的路径。以“当前阶段 → 下一阶段”为一项变更步骤，按企业流程排序；首次进入流程单独记录进入条件。分支在分岔处处理，回退、取消和重开沿用企业实际采用的路径，不强排为通用销售漏斗。

在现有档案维护下表及当前步骤，不要求新建文件或 JSON 契约：

| 变更步骤/分支 | 已有答案及来源 | 变更条件与消息依据 | 相关字段和后续动作 | 自动/人工处理 | 待答问题与状态 |
|---|---|---|---|---|---|

区分“crm-fde 原答案”“待本轮复核”“本轮已收拢规则”和“客户主动跳过”，记录原答案、智能体建议和客户本轮决定各自的来源。阶段名已确定、全表已有草稿或某个条件已获同意，都不自动等于该步骤已收拢。

首次承接或客户要求从头重新演练时，从创建首条记录的条件开始，逐步复核整个流程。原档案已有完整答案也不能跳过这一轮讨论；后面的缺口更明显也不能跳过去。续接同一轮问答时，从本轮首个尚未收拢的步骤继续，已复核的决定直接引用。若客户只调整一条已生效规则，定位该步骤与受影响的后续动作即可，不重走全流程。

## 当前一步怎样问

每轮先明确当前是流程入口还是“阶段 A → 阶段 B”，围绕一个核心业务判断沟通：

1. **带出原定义**：“你在 crm-fde 里原先定义为……”，注明来自该企业档案，不说成 Skill 的既定标准。
2. **给出建议与考量**：结合业务目标和消息识别，解释原定义可能覆盖或漏掉哪些常见情况、建议保留还是调整，以及这样做对客户/商机记录的影响。建议要有理由，不能只把原答案换成“符合吗”。
3. **邀请补充并确认**：用贴近客户业务的场景，问建议是否符合实际，是否还有不同做法或新信息。不要把客户限制在智能体给出的选项内，也不把建议默认当成客户决定。
4. **保存本轮结论**：根据答复补足证据、字段动作与例外；客户已回答清楚就归纳保存，不再对同一答案反复索要确认。

即使原规则看起来完整，也按以上方式说明其适用范围并听取补充；合理时建议保留原规则即可。不为凑问题展开无关的罕见例外。参考 [连续示范](12-worked-example.md)。

围绕当前变化收拢以下内容；旧答案作为讨论起点，本轮已复核的共用答案可以引用，不把这些维度变成逐项机械发问的问卷：

- **触发变化**：发生什么才能从 A 变为 B？多个条件同时满足还是任选其一？
- **识别依据**：WhatsApp、Email、附件或现有档案中的什么事实能证明？谁的表述有效，是否能结合历史上下文？意向、计划、否定、旧版本和已发生如何区分？
- **对象与字段动作**：是哪位客户、哪笔商机？阶段变化时同时更新哪些已采用字段，如何补充或替换旧值，触发什么已有工作流？
- **人工确认与例外**：哪些变化可以自动执行，哪些按企业规则进入“待审核”等统一确认入口？证据不足、内容冲突或本步骤内发生更正时怎样处理？

字段问题随当前步骤展开，例如确认报价变更时讨论报价版本与时间，确认订单时讨论订单金额与收款的区别。跨阶段共用规则只问一次并引用；独立客户资料规则另行收拢，不插入无关问题打断当前变更步骤。内部字段名、API、渠道是否已接通由 Codex 核实，不交给客户做技术选择。

区分“业务员已核实事实”和“业务员必须在 CRM 手工录入”。若客户授权以本人聊天回复为依据，模型可以提取该确认，不额外要求重复手填或固定口令；客户说已付款能否证明到账仍按企业决定，不能自行替换证据来源。

## 收拢后再推进

将当前步骤写成：**从什么状态 → 什么条件成立 → 什么证据支持 → 更新哪些字段/动作 → 自动执行或人工确认，以及不成立时怎样处理**。成立例和不成立例要能区分结果；不要求客户写提示词或测试数据。

当前步骤已带出原定义、建议及考量，并得到客户本轮保留或修订的明确答复，且没有会改变执行结果的未决业务选择，才标为已收拢；接入、映射和运行能力另外标为待实施/待验证。若仍有业务缺口，留在当前步骤继续补问，不把用户对其中一个条件的“符合”扩展为整个步骤已确认。收拢后简述已保存的规则，再进入流程的下一步。

客户主动补充后续步骤时，保存其决定并回到当前问题；客户明确要求跳过或改变顺序时，保存未决项和返回点再继续。客户更正前面答案时，更新相关规则和后续依赖，保留其余已确认结果，不从头重问。

全流程草稿只能作为备课。未决或跳过规则不能混入可启用规则；业务未决只暂停依赖它的更新，独立且已就绪的功能可按授权实施。

## 规则确认与运行判断分开

上述顺序用于配置问答，不要求运行时伪造经过每个中间阶段。消息集中分析时可能已有多步进展，应按企业允许的转换与可靠事件时间判断；跳转、回退是否允许由企业规则决定。

不因阶段名含“确认”就增加客户回复或逐笔审批。例如企业已决定正式报价实际发出即满足变更条件，就识别发送事实，不再添加客户回复“收到”的门槛。现有聊天、邮件、附件和客户档案可以共同提供依据，但只使用实际读取且身份和采购归属明确的来源。

## 输单与停滞按原业务规则二次复核

crm-fde已负责首次主动提出结束规则、确认期限与范围，并对数据就绪的确定性条件优先配置Twenty工作流。先读取其原业务定义、字段来源、工作流及实际状态，再与其他业务步骤一样带客户重新考虑。原档案遗漏时补齐，不把遗漏变成两套Skill的正常分工。在相应分支带出原定义和具体考量，例如：“客户长期不回复或机会一直无推进，可以按约定期限结束为输单，避免商机池失真，也记录下来分析原因。”不能只覆盖明确取消，也不能将“沉默不等于失败”写成禁止所有超时输单。主线收拢不代表输单分支完成。

结合采购周期复核原定适用阶段、期限、计时起点、有效回复/推进、重置、约定延期和自动执行/人工确认；给出保留或调整的建议，接纳新信息。持续推进的长周期采购、已收款和履约中商机是否适用需单独决定；明确采用仅复核就不能擅自自动结束。原答案完整时也给建议与考量、听取本轮补充，不复制其他企业的天数。

不回复与阶段停滞是两类事实：前者依据该客户/采购在已接入来源中的回复情况，销售自己追问不能算客户回复；后者按企业所定阶段停留或有效推进计算，可能仍有普通聊天。以客户确认的时钟为准，不能互换。回复/推进优先同步后再判到期；渠道断连、漏采、跨渠道未关联等导致的未知不冒充不回复，暂停依赖该证据的判定并按需要送待审核。

模型识别对象、有效回复、推进和明确失败的语义及证据；期限由已配置的Twenty工作流或明确指定的唯一执行者计算，不让模型猜是否已满N天。规则未变时保留原工作流，补齐消息事实来源；规则改变时同步调整原工作流的起点、范围、期限、原因与实际生效版本，不新增重复定时关单。按已确认自动策略写输单及主要原因；需人工决定则进入统一待审核。重复批次不重复结束或创建审核，同批次新增回复/阶段变化应先纳入判断。

按 [字段规则](11-field-rules.md) 写入企业固定原因选项。只有符合不回复策略才用客户不回复，仍有沟通但无推进用企业采用的停滞类；明确拒绝有具体依据时记录对应原因，难以归类用其他与说明，不伪造失单动机。结束本笔商机并停止不再适用的销售提醒，保留客户、其他采购、原因历史及未完义务。客户恢复沟通时按已定重开/新机会规则处理。

## 写入模型与执行配置

每一步的决定和来源回写同一企业档案，与 [字段规则](11-field-rules.md) 关联；修改原业务口径时同步受影响的 crm-fde 配置和 Twenty 工作流。记录当前步骤及待答问题，续接时沿用已答内容。

按 [模型配置](09-model-setup.md) 将已收拢规则转成模型说明、输出约束和实际执行条件。每条本次启用或修改的规则至少验证一个成立例与一个不成立/证据不足例；涉及多条件或多商机时覆盖缺项和归属。模型判断、字段变化和真实写入分别验证。不能只改提示而保留程序写死的旧条件。
