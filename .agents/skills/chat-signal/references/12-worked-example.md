# 从规则问答到字段变化：连续示范

以下全为合成情境，只展示方法；阶段、字段、数字和成立条件不是新客户默认值。这里只推演，不发消息、不操作真实 CRM。

## 1. 按流程逐步确认变更规则

crm-fde 在这份合成企业档案中记录：询盘 → 需求明确 → 已报价 → 订单确认 → 履约 → 成功；需求明确处可进入样品分支，各阶段另有失败路径。正式报价实际发出即满足已报价条件；客户确认订单即可进入订单确认，不要求先到账；实际开始履约进入履约，验收完成进入成功。客户级生命周期由订单统计维护。

智能体先简述这条流程，从“创建询盘”开始第二轮梳理。以下对话逐问等待客户答复；原档案看起来完整的步骤也带出定义、建议和理由，不自动略过。

**创建询盘**

智能体：“你原先把客户问价格作为询盘起点。我建议也考虑客户在采购背景下咨询可供产品或定制能力：有些客户先确认能否供应，随后才问价，只识别价格问题可能漏记机会。这样扩展适合你们吗？还有哪些沟通会让你开始跟进一笔采购？”
客户：“这种咨询也算，但供应商向我们推销不算。”

智能体保存客户补充，并围绕本入口继续讨论新采购/原采购的关联和建单动作；入口收拢后才进入需求明确。上述建议和答复只属于这家合成企业，不成为所有客户的默认条件。

**询盘 → 需求明确**

智能体：“你原先要求规格、数量和交货地明确后进入需求明确。我建议结合已有客户资料判断，不要求客户每次重新说一遍城市；本次明确改了地址时，优先采用本次地址，只更新这笔采购，避免把临时交货地变成公司长期地址。这个处理符合你们吗，或还有其他情况？”
客户：“符合，城市可以用已有地址，临时改地址只改本单。”

智能体保存本轮确认及字段动作，结合其他已复核的共同规则归纳成立和不成立情形，当前步骤仍有实际未决项则继续讨论，不因一次“符合”就自动补齐未问的选择。

**需求明确 → 已报价**

智能体：“你原先定义正式报价实际发出就进入已报价。我建议保留这个条件，识别本单的发送记录和版本，草稿或日常价目表不算。这样可以及时开始跟进，也避免把泛泛交流当成正式报价。这是否符合实际，有没有其他报价方式需要补充？”
客户：“符合，我们就按正式报价发出。”

保存本轮结论后，仍在报价步骤讨论相关变更：
智能体：“同一笔采购发出新版报价，我建议更新当前版本，并从新发送时间重算报价跟进时间，避免仍按旧方案催跟进。你们希望这样处理，还是继续沿用原日期？”
客户：“从新版报价发出起算。”

智能体保存版本、时间、阶段和跟进动作，当前步骤收拢后进入订单确认。

**已报价 → 订单确认**

智能体：“你原先定义客户明确接受本单就进入订单确认，不必等到账。我建议保留，并把商机金额记录为客户接受的全单总价，定金单独识别，避免分批付款覆盖整单金额。这个做法适合你们吗，还有哪些订单需要不同处理？”
客户：“适合，金额记全单总价，定金不要写成总价。”

智能体按答复收拢本步证据、总价、币种及自动/人工处理，不把这里的无需到账规则套给其他企业。

**订单确认 → 履约 → 成功，以及分支**

对每一步继续采用“原定义 → 建议及考量 → 客户补充与确认 → 保存变更规则”的方式，样品和失败分支在对应位置讨论。示例在此压缩篇幅，实际问答不能因此跳过这些步骤，也不能将它们标为已复核。

客户中途补充后续步骤时，先保存，再回到当前步骤。记录原答案、建议、本轮决定和待答问题；从本轮最终确认的规则生成模型说明。一次已经回答清楚的结论无需重复确认。

## 2. 形成模型说明和执行动作

| 已确认规则 | 给模型的识别说明 | 程序/CRM 动作 |
|---|---|---|
| 规格、数量、适用交货地齐全 | 综合本次沟通、该商机历史及适用客户地址；意向量不冒充确定需求 | 更新允许的需求字段和商机阶段 |
| 正式报价已发出 | 区分通用价目表、准备发送和该采购的实际报价 | 推进商机；重报价按原文时间更新计时字段 |
| 客户确认订单即可成立 | 识别明确接受与条件性打算；无需额外要求到账 | 进入订单确认，执行企业已有工作流 |
| 金额为已确认订单总价 | 区分总价、报价、定金、运费和更正，保留币种及原文 | 校验后更新订单总价对应字段 |
| 公司长期地址与订单交货地分开 | 说明地点角色及适用采购，不把一次交货地写成公司迁址 | 只更新规则指定对象 |

这份业务说明与实际输出格式、真实字段映射共同使用；表格不是运行配置。业务动作先检查所选程序是否支持。

## 3. 一组跨渠道沟通

客户已在 CRM 唯一登记电话和邮箱，两渠道都已接入，并已验证可按该客户/采购合并上下文。客户生命周期为复购；商机 A 尚在询盘。

- Email：“A 清单，型号 M，20 箱，仍送档案中的地址。”
- WhatsApp：“A 改成 24 箱，其他不变。”
- 销售 Email：“A 的新版正式报价已发，订单总价 4,800 EUR。”
- 客户 WhatsApp：“接受 A 的新版报价，总价 4,800 EUR，按这个订单安排。”
- 后续：“计划先付 1,000 EUR 定金。”

预期：A 的需求是最终 24 箱；适用地址承接已有档案；先识别需求明确、正式报价和订单确认，最终阶段按企业转换规则更新。金额为明确接受的 4,800 EUR；计划定金不替换总价，也不能证明已收款。客户仍是复购，不因 A 的早期阶段回退。联系人总览和 A 的小结分别更新，旧 20 箱不累加。

再收到“另外开 B 单，型号 N，6 箱，交货地稍后给”：明确独立采购，建立 B；按本例规则仍缺交货地，不能借 A 的地址/付款/报价推进 B。这里“交货地稍后给”明确保留了该项待定。

如果渠道尚不能合并，先记录技术缺口、复用各自已验证能力，不宣称模型已经看到了另一渠道的信息。

## 4. 不应变更的对照

“也许下月买一些”“请给我日常价目表”“运费合适就考虑下单”不能分别当作需求明确、正式报价、订单确认。“已付定金”也不自动证明企业要求的收款事实已经核实。供应商给销售邮箱发促销不能建立客户采购商机。

验证时分别记录实际读到的信息、模型事实、目标记录、预期字段变化和实际回读；正常更新按已授权策略自动执行。规则问答的确认不变成每笔业务再次审批。
