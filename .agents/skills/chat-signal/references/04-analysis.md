# 从聊天事实到业务规则

## 每天一次的批量读取与分析

固定采用一天一个常规分析批次，执行时刻和时区由客户决定并保存到客户档案。已有设置直接沿用；缺少时只补问时间，不把“逐条还是批量”作为未定选项，也不擅自固定凌晨 2 点。后台调度发起批次，单条消息到达不触发模型调用。

每次冻结本批次的接收/修订游标上界，读取上次成功处理之后的待处理消息，按客户、会话及采购上下文汇总，结合必要历史分析。边界之后的新消息进入下一日批次；迟到、回补、编辑和撤回按接收/修订增量覆盖，不能只截取“昨天发生”的消息。首次历史导入单独约定范围。

一天一次指业务调度频率，不要求把所有客户塞进一次模型请求。可因上下文或容量限制分组，但保持对话语义与必要历史，不能退化为逐条消息调用。无待处理增量时记录空批次，不为凑结果调用模型。

同一工作区同一调度日的常规批次须去重，按客户时区处理夏令时的重复或缺失时刻。成功游标按处理单元提交；失败或中断保留待处理范围，有界重试/补跑沿用原批次身份，不重复分析已成功单元或重复写入。写入失败优先重试已保存的执行任务，不重新调用模型解释原消息。

业务时间取有证据的消息/事件发生时间，不以批次执行时间替代报价发送或阶段成立时间。CRM 提醒和超时规则各自调度；实施时核对与每日分析的顺序，避免使用未同步的旧阶段误判。向客户说明聊天驱动的更新在每日批次后可见。

## 先归属，再提取，再计算

先将新增消息归属到客户与采购，再提取结构化事实。模型不直接调用 CRM 写接口。新采购与旧采购改量/改规格分开；不凭关键词或产品不同就拆出新商机。有多个合理候选时生成待核对对象与证据，不猜唯一目标。

给路由器精简商机目录：稳定锚点、类别、阶段、采购描述和复核标记。新增采购锚点来自本次有效源消息，继续旧采购使用已知目录锚点。详细提取不得悄悄改绑到另一笔采购。

## 三步组织模型工作

1. **归属判断**：输入本分析单元完整新增往来、客户最近总览和精简商机目录，分为已有采购、新采购、仅客户资料或归属不明。覆盖每条新增信息；归属覆盖不等于每条消息必须产出事实。
2. **事实提取**：按商机读取相关新增往来、适用客户资料、本商机当前字段、最新记忆、关键历史事实与必要原文，结合已确认的阶段及字段规则提取。有意义的新事实才输出；问候、重复收到可没有业务事件。
3. **小结更新**：依据已校验事实、原文和程序计算结果生成联系人总览及各商机专属小结，更新有效需求、进展与待办。新证据完成或取消的事项不继续挂为待办。

同一分析单元优先保留完整新增沟通，再按业务归属分析；不照搬历史实现的固定消息条数或字符数切片。真实模型容量不足时按语义分组并校验覆盖，显式记录未处理部分，不能静默截断。

程序独立维护收发时间、处理回执和修订依赖，不要求模型为每条消息输出占位事件。一条事实用直接支持它的证据；依赖多条记录时保留辅助来源，不拼接不同说话人或订单的内容冒充一条原文。旧记忆是理解辅助，不能凭小结补造付款事实。

客户画像只带相关共用资料，本商机上下文不带其他商机的交易细节。哪些字段可读取、如何更新见 [字段规则](11-field-rules.md)；当前来源的完整性和跨渠道合并能力见 [信息读取](03-ingestion.md)。

## 先完成阶段识别条件梳理

开始设计或修改阶段提取规则时，先按 [逐阶段成立与识别条件](10-stage-rules.md) 与企业逐阶段核对。完整流程是清单，成立条件、消息证据和允许动作是输出；不能根据阶段名称自行补定。“完整覆盖”指智能体核对每个采用阶段，不代表必须逐阶段问客户；先用已有规则和跨来源证据形成判断，仅补实际缺口。仅排查某个已定规则时检查受影响项，不重启全套问答。

## 规则输入

从确认版蓝图生成字段定义、阶段进入条件、事实来源要求、金额口径、单位和正反例；同时核对程序规则和工作流采用同一版本。比如“报价已发出”与“准备报价”分开，“成交”与“收到全部款项”是否同义由客户决定。

泛化事件类别与阶段标签分开。客户采用签约即赢单、打样可选或先建单后交付时，检查引擎的条件/分支表达能力。不要用旧项目的收货/货损/付款组合强套所有企业，也不要认为提示词改了硬编码就自动失效。

## 证据与校验

模型输出含消息/邮件 ID 与 revision，或所用 CRM 档案字段、记录 ID 和版本，以及原文或字段值依据、事实值、适用对象与不确定性。程序校验结构、字段类型、证据存在、客户/商机归属、时间和源消息版本。引用存在只证明能定位原文，仍需样本评估判断原文是否支持结论。

先检查已有客户档案和本商机历史能否补足本次消息未提的信息；本次明确变更优先，适用来源冲突才待核实。已知信息不因本次未提就变成未知，也不要求客户为自动化再复述。真正未知保留未知，不能变成零、无需求或一星。区分谁说的话、已发生/意向/条件句、否定和更正。模型 confidence 不能未经校准就当自动写入成功率。

无新事实可输出 no-change；不能为了每个每日批次有结果而制造更新。结构化输出错误与网络超时分开处理：格式错误可有限修复，持续错误阻断该单元；失败不推进覆盖该单元的成功游标。

## AI 分析失败：最多尝试 3 次并显示系统异常

同一 AI 分析任务最多尝试 3 次，包含首次调用，最多再重试 2 次。任务按工作区、处理单元及其输入/规则版本和模型步骤稳定识别；归属、提取、小结等必要步骤分别记录，已成功步骤复用结果。网络超时、模型接口失败、需要再次调用模型的格式修复均计入对应任务的同一额度；SDK、HTTP 客户端和队列的内置重试必须统一计数或关闭，不能层层叠加。

每次发起调用前原子领取并持久记录尝试次数，避免并发重复领取；进程中断、重启、隔日调度及补跑不清零，也不能给同一失败任务换批次或任务 ID 绕过上限。临时故障在剩余额度内退避重试；明确不可重试的权限、配置等错误可提前停止并报错，不为凑满 3 次重复调用。

每次尝试记录任务/批次 ID、模型步骤、规则/模型版本、次数（1/3、2/3、3/3）、开始结束时间、结果、错误类别及脱敏摘要、可获取的输入输出 token 用量和下次重试时间。用量未知标明未知，不记为零；不把凭据或完整聊天写进错误摘要。

第 3 次仍失败或提前判定不可重试时，停止该任务的自动调用并持久记录终止错误。在统一“待审核”的独立“系统处理异常”区域显示影响范围、尝试次数、脱敏原因、任务定位和排查动作；额度内的失败可显示“等待自动重试”，不要误称永久终止。同一未解决任务去重，恢复成功后退出当前异常列表，历史尝试仍保留。

失败提醒必须能在模型没有产出审核提案时出现。直接读取持久失败状态或使用可靠的错误投递机制；页面不可用时保留待恢复状态，不重调模型来补通知。还要覆盖 CRM 写入失败/冲突，不能只看分析结果或旧 blocked 标记。读取失败显示“暂时无法检查”，不能显示零异常。

技术故障交给 Codex 或维护人员排查，不要求客户在业务审核卡片中批准报错。既有授权包含修复及指定范围恢复时继续执行，不因提醒存在而重复索要授权；授权不含恢复时先准备具体恢复范围再补足授权。终止任务的原错误和次数保留，修复后的有界恢复任务关联原任务，仍最多尝试 3 次；不能用重启或新 ID 无限续命。未修复或未恢复不推进成功游标，不阻塞其他独立单元。恢复结果按正常字段规则处理，不继承任何业务变更批准。页面要求见 [待审核应用](13-review-app.md)，诊断见 [故障经验](14-processing-lessons.md)。

## 金额与数量

订单总额、未接受报价、定金/尾款、退款、单价、运费与历史累计分别提取。币种、单位和费用是否包含要有依据；总额更正保留旧新值关系，退款不自动等于更改整单总额。

程序使用十进制定点或明确精度的金额库，按客户确认的汇率来源、日期与冻结政策换算；不把任何固定换算系数设为通用默认。编码为 Twenty money 之前读取实际字段契约，防止主币单位、minor unit 与 micros 混用；不能假设所有币种都有两位小数。

需求规模、本次选品、实际成交、包装规格分别保存。箱/支/束/公斤不可无依据换算；只把归属一致且口径明确的项目合计。计算由程序完成，模型保留原文数字及语义。数字引用校验须匹配完整 token；`50,000` 不能截成 `50`，分组空格、小数和符号按明确语言/格式处理；不能为了通过校验而去掉来源要求。详见 [回归案例](14-processing-lessons.md)。

## 上下文与小结

日常以增量为主：新增消息 + 客户基础资料 + 该采购最新记忆 + 必要历史原文。不要每次把全部客户历史发给模型，也不要为限额静默丢弃增量。首次历史导入另设批次与范围。

小结帮助理解，不替代证据。按客户总览和每笔商机维护独立记忆；不跨单继承付款、报价、物流。新证据完成/取消/更正旧待办时更新记忆；消息撤回让相关记忆可追溯地失效。

保留必要旧事实引用与按需回取能力。有限滑窗不能保证旧事实还在；需要回查而不可用时明确待核实。小结不展示内部 ID、schema 错误或实现术语，技术原因放运行记录。

生成商机小结前，由程序从当前有效事件和归属目录推导本次必须覆盖的采购集合，以及每笔允许引用的消息/revision；把这份要求显式交给模型。客户资料或无变化事件不凭空要求新商机小结，已知采购可引用核实过的历史。校验失败应区分缺失、多余、错误采购锚点和引用越界，不能只给客户“商机小结失败”的笼统提示。局部商机恢复不得以一条事件覆盖联系人完整总览。详见 [故障经验](14-processing-lessons.md)。

## 成本与质量

记录模型/提示词/规则版本、输入输出用量、重试与每批业务覆盖范围。默认以同一任务最多尝试 3 次限制失败消耗，不设置每日 12 万 token 或其他固定每日 token 硬上限；正常分析用量持续记录。客户另行明确要求预算硬限制时才配置，并保留剩余任务状态与恢复策略，不能以“达到预算”冒充全部处理成功。

先用合成样本做工程回归，再在授权样本上评估漏提取、误阶段、错误采购归属、金额语义和人工覆盖。代码测试通过不能替代业务准确率验收；不在没有测量时承诺节省比例。
