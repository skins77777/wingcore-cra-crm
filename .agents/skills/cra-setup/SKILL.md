# CRA 部署指导

CRA 是供客户 Codex 使用的技术指导 Skill 套装。客户决定自己的管理规则，Codex 根据回答配置客户自己的 CRM 和自动化。交付已有平台上的运行结果，不另建 CRA 应用、管理前端或通用业务规则引擎。

## 从客户已经完成的位置继续

先看当前客户项目的 `crm-foundation/`、已有聊天实施记录和目标环境。没有档案且业务尚未梳理时，读取同套装的 [crm-fde](../crm-fde/SKILL.md) 开始简短问答；不要先问一整页服务器、模型和账号问题。已有答案直接使用，只问会改变当前配置且尚无答案的业务问题。技术事实由 Codex 查证。

本套装的三个 Skill 一起分发，客户档案存放在客户项目，不放进 Skill。若缺同套装文件，先说明缺少哪个入口并恢复安装包，不编造已调用结果。

## 按依赖完成实施

默认顺序：**业务蓝图 → 确定性规则分析 → Twenty 及工作流配置、验证和启用 → 聊天事实接入与模型提取 → 整体联动验收**。前三步由 crm-fde 完成；不能蓝图一完成就转到 chat-signal，把可实施的工作流留给聊天模块。已有实现先核实并复用，局部规则和依赖就绪即可推进，只阻塞依赖未就绪的分支。

| 当前需要 | 执行入口 | 完成结果 |
|---|---|---|
| 形成或修改企业规则 | [crm-fde](../crm-fde/SKILL.md) | 同一份蓝图、字段、决定、AI 可理解的事实与更新边界 |
| 从蓝图识别确定性规则 | crm-fde 的 [工作流分析与实施](../crm-fde/references/twenty/05-workflows.md) | 逐条分析阶段、等级和提醒，记录输入来源、触发、条件/计算、动作、执行者及依赖 |
| 安装或配置 Twenty 及所选工作流 | crm-fde 的 [Twenty 实施经验](../crm-fde/references/twenty/00-index.md) | 客户自己的实例、字段及实际映射；所选工作流已配置、验证并按授权启用，缺口分别记录 |
| 聊天接入、模型配置、自动更新 | [chat-signal](../chat-signal/SKILL.md) | 接入需语义理解的事实，配置其提取与写入，复用并验证已有工作流的后续计算 |
| 保留并配置“待审核”应用 | [待审核应用指导](../chat-signal/references/13-review-app.md) | 在业务与识别规则确认后，将全部需人工确认的拟变更接入统一入口，并验证决定到执行 |
| 验证和日后调整 | 两个 Skill 各自的验收与维护指导 | 真实结果、运行责任、恢复办法和可续接记录 |

部署只分 **VPS 版和本地版**，沿用客户已有选择；已完成部分不重装。VPS 版将 Twenty、消息接收、业务数据库、队列、调度、分析编排、审核后台与 CRM 写入部署在 VPS，以 2 核 4 GB Linux 为起点，按实际组件和负载验证。本地版先核对各组件实际位置、依赖与电脑持续运行条件，不把旧混合云经验套给新客户。模型默认接外部 API；本地部署不等于本地推理，明确要求模型权重本地运行时再评估资源，不悄悄升配。

公网入口单独选择，Cloudflare、自有域名、Vercel、GPT 站点等只在访问方案中按需考虑，不作为第三个部署版本。VPS 版不再让客户选择这些平台承载业务队列、定时分析或写入执行。入口方案、适用条件与验收见 [部署与公网访问](../chat-signal/references/02-deployment.md)；Twenty 安装与对外地址配置见 [安装指导](../crm-fde/references/twenty/01-installation.md)。仅本机使用且无外部回调需求时不强制公网入口。

客户的业务规则是提取规则的基础。chat-signal 先以完整商机流程为清单，逐阶段问清成立条件、WhatsApp/Email 等信息的识别依据和更新动作，并核对客户、联系人及商机字段：已有答案沿用，实际沟通中的缺口用具体场景补问，决定仍写回同一档案。随后生成模型输入、输出约束及真实字段映射，不重做基础 CRM 访谈。规则、提示、映射与工作流记录同一个业务版本；不要把某种 JSON 格式当成所有客户的必选架构。

交接给 chat-signal 的是已实施的基建、工作流版本及待接入事实，不是尚未执行的工作流清单。仅需数值、日期和明确条件的判断不调用模型；例如成交金额、订单数或采购潜力变化后，由工作流按企业规则重算等级和安排提醒。需要聊天语义时拆成“模型提取事实 → 事实入库 → 既有工作流计算”，避免模型与工作流同时写派生字段。规则复核有变化时同步调整原工作流及映射，保持唯一执行者。

## 部署时保持精简

- 先复用客户已有服务和 Twenty 原生能力，再为实际缺口选择运行组件。后台组件负责持续采集与分析；Codex 负责安装、配置、调整和排错。
- 运行组件必须有客户可取得的源码或发布产物、版本、依赖和启动方法。没有时按已授权范围在客户项目补最小实现；不能把缺下载包变成开发通用平台，也不以“这是 Skill”结束可完成的工作。
- 不默认要求 Cloudflare、Neon 或某个固定聊天渠道。随包保留 Twenty 待审核应用；客户完成 crm-fde、chat-signal 的相关业务规则后配置审核范围、成员与应用。已有等价入口直接复用；普通自动更新遵循已确定策略。
- 不执行旧 CRA 配置编译、候选模拟、审阅声明或发布归档流程作为部署前置条件。工具只有实际减少实施错误时才使用。
- 继续已经授权的部署与可逆配置，不制造逐步签字流程。凭据由客户在安全位置提供，文档只存引用。当前套装制作不授权操作作者或其他客户的生产环境。

## 怎样算这家企业已经部署好

先核实 crm-fde 的基建结果：客户能打开自己的 Twenty，使用符合其规则的字段和流程；对已采用的确定性规则，用真实字段变化或定时触发验证阶段、等级及提醒结果，确认计算链路不调用模型，保存工作流/激活版本、运行证据和 CRM 回读。只建字段、保存草稿或手动运行不能代替工作流启用与真实触发验收。

再核实聊天联动：约定渠道的新消息能被后台收到，模型按该企业规则提取所需事实或提出其负责的字段变更，程序执行允许的写入，既有工作流完成其负责的后续计算，Twenty 回读符合预期。验证一个不应更新的反例，以及实际启用功能的重试、人工修改和调度行为。未采用的能力不强制部署，数据或平台缺口具体列出，不把局部完成写成整套上线。

把实际结果回写同一企业的实施和验收记录，区分已分析、已配置、已验证、已启用及待处理。客户再用 Codex 做一次低影响调整并验证。仅安装 Skill、生成规则或通过本地检查都不代表完成该企业部署。
