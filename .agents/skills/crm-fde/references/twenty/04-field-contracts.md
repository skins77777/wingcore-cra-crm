# 字段含义与 Twenty 编码

适用：选择字段类型、API/导入映射、金额和枚举排错。业务定义先读 [字段教材](../03-fields.md)。这里保存技术编码经验，不用它替客户决定业务。

## 每个字段要说明到可执行

一张字段卡应包含：归属对象、客户可读名称、业务定义、单位/币种/周期、类型、空值含义、来源与更新者、内部名、API 编码、关联对象、所驱动的规则及一条验收样例。客户只需先理解“记录什么、帮什么决定、什么时候更新”；编码由智能体负责。

| 管理概念 | 放哪里 | 避免的问题 |
|---|---|---|
| 客户整体价值与关系状态 | 公司/客户 | 不用某一笔商机的状态覆盖全部客户关系 |
| 某次需求、报价、赢单、输单 | 商机 | 同一客户多笔需求保持独立 |
| 一笔确认订单的金额/数量/日期 | 订单（本项目自定义 `sales`） | 累计统计从明细得出，别把定金当订单总额 |
| 联系人的持续跟进摘要 | 联系人 | 不与商机专项摘要混合 |
| 某次沟通事实 | 备注或其他已选记录入口 | “覆盖最新摘要”与“保留历史事实”是不同用途 |
| 下一步动作及完成状态 | 任务 | 提醒消息不自动等于任务已完成 |

`sales` 是原项目的自定义对象路由；新实例未必存在。先检查已有订单对象，含义相同就复用。不要因为文档用了这个名字便重复创建。

## 显示标签、内部值、排序分别保存

原项目历史阶段示例：

| 显示标签 | 内部 value |
|---|---|
| 询盘 | `NEW` |
| 需求确认 | `SCREENING` |
| 报价 | `MEETING` |
| 成交 | `CUSTOMER` |
| 配送 | `PROPOSAL` |
| 赢单 | `YING_DAN` |
| 输单 | `SHU_DAN` |

这张表说明为什么不能凭英文名称猜业务意思；它不是给所有客户的阶段模板，也不覆盖已确认的打样分支。商机流程应按 [流程教材](../05-process.md) 先确认完整节点。

- 改“备货”为“配送”可能只改 label，已有 value 可以保留；若业务意义改变，则要评估记录、过滤器和工作流。
- 枚举 position 与看板分组 position 可能各自存在，两处均需检查。
- 评级本项目编码为 `RATING_1` 至 `RATING_5`，不是页面的星号，也不是直接传整数。
- 原任务状态为 `TODO`、`IN_PROGRESS`、`DONE`；完成或取消的业务区别不能硬塞到不存在的状态中。
- 多选字段类型与某个写入适配器当前仅支持一个值是两回事。原产品适配器只放行一个已知产品类别，不能推断 Twenty 不支持多选。
- “缺乏认证”保留为外贸输单原因推荐选项，汇总其出现次数可辅助经营判断；不要自动扩展认证专项流程或把它变成必填原因。

## 本项目已使用的复合值

以下是源代码及受控试点中的编码例子，目标版本仍要从实际字段 schema 验证。

```json
{
  "name": { "firstName": "完整原始姓名", "lastName": "" },
  "followUpSummary": { "markdown": "本次跟进内容", "blocknote": "" },
  "amount": { "amountMicros": 1234560000, "currencyCode": "CNY" }
}
```

这些属性可能属于不同对象，不是一个可直接提交的整条请求。

- 姓名：不根据姓名语言猜姓/名。本项目的保守策略是完整姓名放 firstName；新客户已有拆分姓名时保留其结构。
- 富文本：本项目 RICH_TEXT 使用 `{markdown, blocknote}`。写入后既回读也检查页面渲染；已有编辑器内容不能无条件覆盖为空。
- 电话/邮箱/地址：可能同样是复合结构；本手册未提供它们的完整 payload，实施时读取当前 schema 和测试记录，不能当普通字符串猜写。
- 时间：包含时间的字段使用明确时区的时间值；仅日期的业务字段不应凭本机时区转成上一天或下一天。
- null、空数组、空字符串、“没有收到资料”含义不相同。没有采购量不是采购量零，也不应自动判为一星。

## 金额：一元不是一个 amountMicros

本项目 Twenty CURRENCY 使用 `amountMicros`：一主币单位对应 1,000,000。上例 1,234.56 元对应 1,234,560,000 micros。

若业务层按人民币/美元的分保存整数，则 `amountMicros = amountMinor × 10,000`。原适配器检查整数、安全整数上限及货币代码，再编码；不要先把 6,328 美元转换成 6,328 micros。上述“分”模型仅覆盖当前两位小数币种，不直接适用于所有币种。

实施时分开保存并定义：

| 值 | 必须说明 |
|---|---|
| 原币订单总额 | 币种、是否含运费/税费、何时确认 |
| 定金/尾款 | 实际收款还是约定收款，来源与日期 |
| 报价金额 | 是否正式报价，是否可作为预计商机金额 |
| 人民币统计金额 | 汇率来源、日期、四舍五入规则、是否冻结历史值 |

优先使用十进制定点计算或已验证金额库；四舍五入到业务约定精度后再转 micros，防止浮点尾数污染累计统计。原项目曾用固定非人民币换算系数，那是公司当时的临时规则，**不作为安装默认汇率**。

原适配器拒绝负数，是该写入入口的限制；退款、冲销不能偷偷改成负订单后认为规则仍成立，需另定处理口径。客户阶段、订单数、累计金额都应在修正后可核对。

## 验证一项字段配置

1. 读取元数据，核对对象、内部名、类型、激活状态、可空性、选项与关系方向。
2. 在明确的测试记录填入正常值和边界值；金额至少包括小数、原币与统计币，评级包括未知与阈值边界。
3. 通过 API 回读原始值，检查页面显示、筛选和相关工作流输入。
4. 验证普通人工修改入口能用。字段存在但用户无法正常维护，不算交付。
5. 记录只影响显示还是影响业务规则，告诉客户未来改名称、选项、单位分别会影响什么。
