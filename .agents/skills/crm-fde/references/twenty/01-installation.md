# 安装、地址与持久化

适用：新装、接管已有 Twenty、确定本地或托管形态。升级另读 [02](02-upgrade-recovery.md)。来源：原项目 Compose、环境示例、迁移执行记录；精确文件见 [10](10-provenance-script-audit.md)。

## 先形成环境卡

智能体能读取的信息自己核对，不把全部技术问题交给客户。记录：

| 项目 | 要弄清的事情 | 用途 |
|---|---|---|
| 使用形态 | 已有 Cloud、自托管服务器、个人电脑 | 决定谁维护服务、是否一直在线 |
| 目标身份 | 实例地址、工作区 ID、测试/正式 | 防止配置到另一家公司 |
| 软件基线 | server、worker、数据库、Redis、定制镜像 | 判断兼容性与恢复材料 |
| 运行环境 | Docker context、主机架构、可用资源、磁盘 | 防止连错容器引擎或空间不足 |
| 持久化 | Compose 项目、真实卷名、挂载路径 | 防止新建空卷被误认为数据丢失 |
| 访问方式 | 浏览器地址、容器内部地址、API 地址 | 避免 localhost 和公网入口混淆 |
| 运维责任 | 谁开机、谁备份、谁处理故障 | 区分个人可用与客户可持续使用 |

对客户可以只说：“系统装在你的电脑上，电脑关闭时就暂时不能使用。我们先确定由电脑还是长期在线的服务器承载。”不要因讨论承载形态就购买服务或迁移现有数据。

CRA 只分 VPS 版和本地版。VPS 版的 Twenty、业务数据库和后续聊天自动化后台均在 VPS，模型通过外部 API 调用；本地版核对电脑系统、Docker、资源与实际组件位置。本地部署不等于离线推理。已有托管实例是需复用或明确迁移的现状，不因此新增第三种后台版本。

## 本项目经过验证的组成

以下是历史安装基线，不是“所有客户必须固定此版本”的模板。

| 组件 | 本项目配置 | 提炼的经验 |
|---|---|---|
| Twenty server / worker | 两者均 `twentycrm/twenty:v2.40.0` | 同一次部署锁定并核对版本，不能只升级 server |
| PostgreSQL | 16，命名数据卷 | 升级应用前检查数据库兼容性；数据卷单独保护 |
| Redis | 7.4，`noeviction`，命名卷 | 使用对应版本支持的队列配置；连通 Redis 不等于 worker 正在消费 |
| 本地文件存储 | server、worker 共享 `.local-storage` 卷 | 只备份数据库不能恢复附件；两个服务都需正确挂载 |
| Compose 项目 | 历史名 `twenty-local` | 接管升级保留已存在的项目名与卷映射；新客户自行命名 |
| 主机入口 | `127.0.0.1:3002` 映射容器 3000 | 这是个人本机访问配置，不是团队公网部署 |
| 逻辑函数 | `LOGIC_FUNCTION_TYPE=LOCAL` | 这是本项目执行方式，换部署需核实目标版本支持 |
| 邮件驱动 | `EMAIL_DRIVER=logger` | 邮件写日志不等于邮件送达；不宣称找回密码/邀请已可用 |

历史 Compose 中 server 负责迁移及 Cron 注册，worker 的 `DISABLE_DB_MIGRATIONS` 与 `DISABLE_CRON_JOBS_REGISTRATION` 均为 `true`，启动 `yarn worker:prod`。server 对应开关为 `false`。以后采用目标版本官方配置，不盲目复制旧开关。

## 新安装的执行顺序

1. 获取选定发布版本对应的官方 Compose 和环境示例，先检查内容；记录版本和来源。不要下载移动中的配置后声称已经锁定整个部署。
2. 检查 Docker context 与目标目录，确认端口未被占用、卷命名不会误接别的客户。参数中的密码、URL 和特殊字符按实际解析方式处理，不能使用简单字符串拼接猜测转义。
3. 生成本实例独有密钥，存入受保护的部署配置或凭据存储。新装按目标版本文档设置，**不套用旧实例“ENCRYPTION_KEY 等于旧 APP_SECRET”升级规则**。
4. 检查环境变量确实传到需要它的服务。仅写 `.env` 而 Compose 未引用，服务可能仍拿不到值。调试时只报告是否存在、是否匹配，不打印整份已展开环境。
5. 启动数据库与 Redis，再观察 server 初始化/迁移、worker 启动。首次迁移可能较慢；历史 server healthcheck 预留了 8 分钟起始期，这不是所有客户都需要等待的固定时长。
6. 检查服务、登录、工作区、附件、API、测试任务/工作流与页面。通过后才开始客户业务配置。
7. 完成首份可恢复备份，记录日常启动、停止、备份入口和责任人。开机自启、实际定时执行另行验收。

官方当前文档提供 Docker Compose 安装与持久化说明；其中 `SERVER_URL` 应与客户实际访问地址一致，常规域名部署需配置 HTTPS。新装时重新核对发布版本要求。[官方 Docker Compose 文档](https://docs.twenty.com/developers/self-host/capabilities/docker-compose)

## 按需配置公网入口

只在本机使用且没有外部回调需求时可以跳过。需要公网 HTTPS 时，优先复用客户已有资源，可选自有域名加 VPS HTTPS 反向代理、Cloudflare 代理或 Tunnel、Vercel 项目网址加外部转发；GPT 站点（ChatGPT Sites）作为候选，先核实并验证连接 VPS、身份认证和完整转发能力。仅 API 调用成功不等于 Twenty 整站可用，不为获得网址另建 CRM 前端。

这些选项都服务于公网访问；Twenty 仍在客户电脑或 VPS，VPS 版不使用入口平台运行业务队列、定时分析或 CRM 写入。域名需配置 DNS/证书，托管转发需能访问源站，本地入口需隧道等可达连接；不能用外部平台直接访问客户的 localhost。旧私有隧道也不会自动被新平台复用。

记录浏览器入口、`SERVER_URL`、内部 API 和实际回调地址。切换入口时同步相关配置，保持鉴权且不公共缓存 CRM 私密内容；从实际外部网络验证登录、刷新、保存、附件上传下载及采用的 SSE/WebSocket，不能只凭首页可见判通过。聊天渠道接入时另行验证回调，后台调度单独验收；替换入口不重复启动业务执行器。

实施时核对 [Cloudflare Tunnel](https://developers.cloudflare.com/tunnel/get-started/)、[Vercel 外部转发](https://vercel.com/docs/routing/rewrites)、[ChatGPT Sites](https://learn.chatgpt.com/docs/sites) 的当前能力和限制，记录所选方案的实测结果。本节是实施指导，不表示各平台已在客户环境验证。

## 三种地址不能混用

| 请求从哪里发出 | 本项目例子 | 注意 |
|---|---|---|
| 主机浏览器 | `http://localhost:3002` | 指主机回环地址；其他同事电脑访问不了此地址 |
| 同一 Compose 网络中的函数/进程 | `http://server:3000` | `server` 是本项目服务名；若重命名服务，地址相应变化 |
| 客户的远程浏览器 | 客户实际 HTTPS 域名 | 需独立部署入口；本项目没有验证通用公网安装方案 |

历史故障：Writer 在容器里使用主机回环地址无法访问 Twenty，任务进入可重试状态；改为内部服务地址后通过。遇到连接错误，先确定调用者所在的网络空间，再检查端口，别直接放开公网端口。

## 验收与限制

- 重新启动后，已有测试记录和附件仍在，证明不是临时容器文件系统。
- 从正常登录入口进入客户、联系人、商机页面；不能只用保存过状态的旧浏览器标签。
- 后台工作由 worker 实际完成，日志没有持续迁移/队列错误。
- 个人电脑的休眠、关机、Docker 停止意味着本地不可用。原项目混合云还能接收消息的能力来自额外云端组件，不能承诺给只有本地 Twenty 的客户。
- 本次经验提炼没有验证公网 TLS、邮件投递、生产容量、多人并发或任何新客户安装；需要时放进该客户验收项。
