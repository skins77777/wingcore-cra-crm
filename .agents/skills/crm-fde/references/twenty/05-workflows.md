# 确定性规则分析、工作流部署与统计一致性

适用：从业务蓝图识别阶段、等级、提醒及统计的确定性规则，配置、验证并启用 Twenty 工作流，以及迁移和处理已有流程干扰。业务规则以客户蓝图为准；聊天语义提取不在这里实施。

## 从客户业务规则主动识别自动化

先完成本次范围的业务蓝图，再由 crm-fde 逐条分析已采用规则，不等待客户提出“这个字段能不能自动改”。复用阶段条件、等级阈值、聚合方式、提醒周期和数据来源；技术可行性由智能体查证，不让客户重答业务问题。仅局部就绪时先完成该部分，其余保留具体依赖。

判断依据是**输入是否明确、规则是否能确定计算结果**，而非字段叫什么或是否最初来自聊天：

| 规则性质 | 执行方式 | crm-fde 的落实职责 |
|---|---|---|
| 已有结构化字段足以做比较、计算、日期判断或状态映射 | 优先 Twenty 事件/定时工作流，必要时使用工作流内的 Code/函数；运行不调用模型 | 核实目标能力后配置、验证并按授权启用 |
| 输入需先理解聊天，但后续结果可确定计算 | 拆为“提取事实 → 写入事实字段 → Twenty 工作流计算并更新” | 负责后半段工作流；核实事实来源，缺失时记录并准备可配置部分，依赖未就绪的分支不启用 |
| 条件需要业务员决定，或客户明确要求人工维护/确认 | 保留人工边界，拟变更需审核时接统一入口 | 不把可计算误当允许自动执行；分别记录规则与入口就绪状态 |
| 数据不足、规则待定或目标能力缺失 | 只阻塞受影响动作，记录缺口和可行替代 | 不用大模型猜缺失值或代替确定性计算，不默认另建运行引擎 |

核心盘点必须覆盖客户关系阶段、商机阶段、客户等级和已采用的提醒规则；客户未采用的项目记录跳过。阶段的业务条件已由可靠字段证明时，可以由工作流推进，不能因为默认入口是人工就漏掉这种自动化。聊天中一句“已付款”与核实到账字段不同，不擅自改变证据标准。

以下仅演示分析方法，数值和结果不能成为新客户默认：

| 客户已确认的规则与输入变化 | 确定性执行 |
|---|---|
| 成交金额 10 万变为 30 万；按该企业分档，对应等级由 2 星变 3 星 | 金额变化触发，按完整分档重算，再按聚合与升降规则更新等级 |
| 成交订单数 2 单变为 10 单；按该企业分档，对应等级由 3 星变 4 星 | 次数变化触发，同样计算最终等级；不依赖模型分析订单数量 |
| 金额对应 3 星、次数对应 4 星；企业选各指标取最高 | 同一套评级逻辑读取全部采用指标，输出 4 星；不能两条流程各自覆盖综合等级 |
| 企业以已核实的业务字段组合作为某阶段成立条件 | 相关字段变化后检查当前阶段及全部条件，更新允许的阶段并维护进入时间 |
| 企业规定进入某阶段后一定时间提醒，或无活跃商机时按等级维护 | 工作流计算到期并创建待办，沿用负责人、去重、完成后再提醒和停止规则 |

把结论写入蓝图的“确定性规则与工作流分析”，技术映射及证据继续保存在 implementation.md、acceptance.md；已有等价表原位补齐，不强制额外 JSON。每条规则明确输入与来源、触发、条件/计算、输出动作、执行者、依赖和实施状态。分析只说明应如何实现，不能标为已配置。

## crm-fde 完成配置、验证和启用

1. **核实平台与数据**：读取目标版本的官方资料及实际能力，核实字段类型、金额单位/币种、枚举、时间来源、关联和已有工作流。Twenty 官方的 [公式计算示例](https://docs.twenty.com/user-guide/workflows/how-tos/crm-automations/formula-fields) 演示“记录更新 → Code 计算 → Update Record”，具体入口以目标版本实测为准；Code 是确定性代码，不是模型节点。
2. **配置完整依赖链**：在本次 Twenty 部署/配置中一并落实所选工作流。统计值尚未可靠维护时，先配置有效订单的汇总，再接评级；不能只配置评级却把失真的累计值当事实。已有等价工作流优先复用，分析出的可实施项不能全部留待 chat-signal。
3. **限定触发与写入**：只在相关输入变化或约定到期时计算；执行前读取所需当前值，结果不同才更新，防止写回自身形成循环。综合等级有唯一计算者，遵守未知/零、只升不降及授权纠错；提醒按当前阶段和活跃商机重新判断，失效任务不继续执行旧计划。
4. **实际验证**：按客户阈值检查边界和跨档跳变、多个指标聚合、空值、重复触发及人工纠错；阶段规则检查成立/不成立及企业允许或禁止的回退，提醒检查到期/未到期、去重和停止。记录真实触发、运行步骤和 CRM 回读；确定性工作流链路不含模型调用，模型映射也不另写同一派生字段。没有目标连接只报告已设计及缺口。
5. **启用并交付**：通过相应验证后按已有授权启用，核实实际激活版本和生产事件/定时运行证据。分别记录已分析、已配置、已验证、已启用；仅保存草稿或手动运行不等于生产链路通过。交付工作流与字段映射、唯一执行者及待接入事实，chat-signal 复用这些成果。

混合规则中，模型只提取确需语义理解的事实；例如采购潜力入库后，分档、综合等级和维护到期判断都由已配置工作流执行。运行时不为这些计算再次调用模型。业务规则改变时，由当前实施者同步调整同一工作流及映射并验证，不另起一套竞争写入。

## VPS 标准地址同步由 crm-fde 实施

套装内的 [VPS 参考包读取说明](../../../chat-signal/references/15-vps-deployment.md) 提供 v5 脱敏配置与来源清单，其中含地址同步 service/timer；完整同步业务实现仍须按客户字段映射取得或适配。

由 crm-fde 在 CRM 基建阶段为每家选择 VPS 版的客户部署并验收“关联客户地址 → 商机客户地址”的同步能力。功能属于标准交付；各客户的工作区、对象关系、字段内部名和字段 ID 按实际元数据配置，不能沿用作者实例的固定值。缺少字段或映射时补齐该部署项，尚未接通则标为待完成，不能将功能降为可选或直接跳过。

默认使用关联客户地址作为商机客户地址的来源；客户地址更正、商机关联客户改变后同步更新。商机收货地址若是另一个业务字段，应分别映射，不能将它误当作客户地址镜像覆盖。人工更正优先修改来源客户地址；历史字段承担其他用途时先明确映射并保留原数据。

这是 CRM 已有结构化字段间的确定性同步，独立于聊天接入和模型。crm-fde 负责字段与关联、执行实现、配置启用、回读验收和后续维护；chat-signal 只复用已交付能力。原 VPS 使用独立定时脚本通过 Twenty API 同步，不能误称为 Twenty 原生工作流；执行在独立服务并不改变基建归属。已有可靠实现优先复用；新装先核实 Twenty 原生工作流能否满足规则，不足时由 crm-fde 配置必要的确定性同步服务，不推迟给聊天模块，也不为改职责重复部署或替换线上实现。

实施时核对客户对象、商机对象、客户关联字段、源/目标 ADDRESS 字段的身份与类型，以及目标工作区。参考实现通过独立 service/timer 每轮结束约一分钟后同步，与主写入器共用数据库锁，写入前重新读取关联与来源，用版本条件防止覆盖并发修改；同值不重复写入。不调用模型，也不等待每日分析批次。已有等价实现可以复用，但同一目标字段只保留一个维护者。

记录来源明确清空、解除关联时的镜像清空策略；来源记录缺失、权限不足、字段未返回与真正空地址要区分，前者报错或保留待处理，不能当空值批量清空。验收包括首次同步、客户地址变化、关联客户切换、空值/解除关联、来源缺失、重复轮次、并发冲突和重启恢复，记录 CRM 实际回读与真实定时触发。

## 先做依赖图

本项目的五条业务流程形成以下关系，供理解分工：

```text
商机进入客户定义的赢单条件
  → 校验并创建或同步对应订单
订单新增 / 删除 / 修改
  → 更新客户订单数量与累计成交额
客户统计变化
  → 更新客户关系阶段与星级
```

这不是每家企业都必须安装的五条固定脚本。“订单删除回冲”仅描述已有数据事件的处理，不授权删除订单。客户选择取消/作废替代删除时，应按其记录方式设计统计。

赢单、付定金、发货、收齐尾款可能不是同一个时刻。必须沿用已经确认的阶段含义，不能看到“成交”两个字就提前建单。可选打样、输单及输单原因也不能被这个示意图省略掉。

## crm-fde实施停滞或不回复的期限工作流

客户在crm-fde中确认期限、阶段范围、时间依据、重置/延期及自动输单或人工确认后，优先用目标Twenty支持的工作流完成这条确定性规则，不把它推迟到chat-signal才设计或依赖模型每天判断天数。以下是实施步骤，需核实目标版本、权限和实测能力，不能把参考步骤当已部署配置。

1. **核实数据**：映射阶段、计时字段、延期/排除条件与输单原因选项。阶段进入时间由真实阶段变化维护，普通编辑不重置；以有效回复为依据时确认其时间字段与来源确实可用。未接入消息不能用空日期证明不回复，只暂停依赖这项数据的分支。
2. **核实触发能力**：检查目标版本可用的定时/到期触发、条件筛选、日期比较和更新动作；必要的函数依赖也须实测。按客户时区与精确边界配置检查，不猜内部参数。原生能力不足时记录缺口及必要补充方案，不能声称工作流已完成。
3. **复核当前记录**：每次执行重新判断当前阶段、有效计时起点、期限及延期/排除条件；排除赢单、已输单和企业未授权的阶段。与阶段或有效回复更新的先后要验证，旧的延迟任务不能在客户已回复、商机已推进后继续执行旧关闭计划。
4. **执行企业动作**：自动结束则一致保存输单阶段、合法主要原因及结束依据/时间，并停止不再适用的销售提醒；人工确认则创建已选的复核/待审核事项，先不改输单。不回复原因必须有无回复依据，阶段超时但仍有沟通不能冒充不回复；保留客户、其他商机和历史。
5. **处理重复与并发**：同一商机的同一次到期不重复结束或建复核事项；记录已处理依据，人工改动或更新计时后重新校验。只在读写具备实测保护时宣称可避免并发覆盖。
6. **验证并启用**：在授权范围验证未到期、恰到期、回复/推进后不满足条件、排除阶段、空时间、重复执行和延期；真实定时触发及CRM回读另行记录，草稿保存或手动运行不代表生产调度成功。
7. **交接复核**：保存业务版本、工作流/激活版本、触发时区、时间字段来源、唯一执行者、验证结果及待接入项。chat-signal读取这些记录，随其他步骤重新考虑业务规则；未变则保留工作流，只接入需要的消息事实，修改规则则同步修改原工作流，避免后台另起一套同条件关单任务。

如果客户已存在合适的期限工作流，先核对并复用。实施职责与业务建议分开记录：规则已确认但来源或平台能力未就绪时，清楚标为未实施，不改写客户选择。

## 导入步骤完整，不只复制标题

工作流记录、版本、触发器、步骤、代码函数及其引用都要检查。本项目最初单独补导出了 8 个被引用的 Logic Function 源码，才覆盖业务与系统工作流依赖。

迁移时：

1. 记录源流程用途、当前激活版本、依赖字段、Code Function、触发条件和测试例。
2. 按 [元数据映射](03-metadata-migration.md) 解析目标对象与字段；缺引用就先阻止该流程导入。
3. 在目标创建草稿，检查嵌套条件、变量表达式、函数版本及上下游输出。
4. 深度比较源/目标 trigger 与 steps；源 UUID 变为目标 UUID 后比较语义，而不要求所有安装身份字节相同。
5. 测试范围内行为，再按已有授权激活；检查目标激活版本、事件注册和 worker 执行证据。
6. 新旧流程并存时先明确谁负责事件，避免一次新增订单触发两套统计。旧流程优先停用并保留回退依据，不默认删除。

本项目通过 `duplicateWorkflow` 复制过内置流程，并由平台克隆代码函数。那是当时接口与权限下成功的做法，目标版本需核实可用入口；不能拿原脚本自制 JWT 或写 core 表作为正常安装步骤。

官方文档区分草稿与激活版本：编辑草稿时，原激活版本仍可运行；修改完必须检查真正生效的版本。[官方工作流版本文档](https://docs.twenty.com/user-guide/workflows/capabilities/workflow-versions)

## 防止内置流程覆盖客户关系

原项目出现过一个需要保护的入口：创建联系人时已明确关联公司，但内置 `Create company when adding a new person` 仍可能生成占位公司并改变关联。

当时修复是在该流程触发器上增加 `after.companyId IS_EMPTY` 条件。实测“已经有关联公司”的联系人没有触发该流程，关系保持不变。

复用时先检查目标流程现有条件，并把“关系为空”与原条件正确组合，不能整组覆盖原筛选器。至少验证：

- 已有公司关联：保持原关系、不新建占位公司。
- 无公司关联：依客户所需行为执行；若保留自动建公司，再验证成功路径。
- 用户之后人工更改关联：没有另一个旧流程把它改回。

历史记录只证明其中已经关联公司的防护用例，不自动证明所有正向、空值和并发分支。

## 重复建单与统计漂移

“先查没有订单再创建”在并发下可能两次都查到空。一个顺序测试通过不等于原生工作流具有原子唯一性。

实施建议：给每笔业务定义稳定关联键，例如同一来源商机与订单的唯一关联；核实平台是否支持需要的唯一约束、幂等动作或并发控制。不具备就明确限制并提供人工复核，不能宣传严格一次。

| 情况 | 应验证的结果 |
|---|---|
| 赢单事件重放、同一阶段再次保存 | 同一笔订单，不重复累计 |
| 赢单退出后重新进入 | 按客户规则更新原单或另建，不能自行猜测 |
| 订单金额修改 | 只反映差额，或从有效明细重新汇总 |
| 订单换客户 | 原客户减少、新客户增加；不只改新客户 |
| 订单取消/删除事件 | 按约定回冲一次，空值与零区分 |
| 两笔订单接近同时完成 | 最终统计等于有效订单明细，无丢失更新 |
| 手工修正累计值 | 有明确权威来源，不被两套流程互相覆盖 |
| 工作流失败后重试 | 副作用不会重复；有实际证据 |

增量统计速度快，但失败补偿、重复事件、乱序和改绑需要处理；从有效订单重算更容易核对，但要确认规模与执行成本。让智能体根据能力选择，不把历史差额脚本当通用正确性证明。

## 分级与阶段的边界

客户星级可能取多个指标最高；采购潜力与累计成交是不同来源。工作流只拿成交额重算并覆盖综合星级，会丢掉采购潜力的贡献。需明确综合规则、未知值处理、是否只升不降以及手工纠错方式。

客户关系阶段与商机阶段分开：一笔输单不自动把老客户改成无价值客户；某笔赢单不自动完成其他商机。执行前检查所有会写同一字段的工作流，标出唯一责任或组合顺序。

## 验收证据

保存“触发前记录 → 输入事件 → workflow/version → run/步骤结果 → 订单和客户回读 → UI”。ACTIVE 标签、代码编译成功、一次手工 Run 都不等于真实数据库事件链已运行。

迁移记录证明五条业务流程已映射、激活且注册触发器，不足以证明所有新客户规则、订单并发与边界均通过。把本页测试矩阵按实际范围加入客户验收，未执行的标为待验证。
