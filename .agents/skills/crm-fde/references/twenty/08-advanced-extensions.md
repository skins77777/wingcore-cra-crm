# 扩展附录：Twenty App、凭据与外部写入

**其他 Skill 承接相关模块或用户明确扩大本次实施职责时，按需读取。** 客户版保留统一待审核能力，业务与识别规则完成后由 chat-signal 配置 [随包应用](../../../chat-signal/references/13-review-app.md)。基础 CRM 教学不提前安装；渠道连接器按需配置。VPS 版后台统一在 VPS，公网平台仅负责接入；下文的外部 Worker、云数据库及迁移经验用于理解历史实现，不作为新客户的额外后台选项，不能照抄作者配置。

## 原生 App 的组成

本项目使用 Front Component、Page Layout、Navigation Menu Item、服务端 Logic Function 和 Application Variables 构建待审核页面；未修改 Twenty 核心源码。页面部署与功能可用要分层验收。

| 层 | 需核对 | 典型遗漏 |
|---|---|---|
| App 身份 | application 与实体 universalIdentifier、安装归属 | 复制一个不属于目标发布者的身份造成冲突 |
| 依赖 | server、SDK、Node、构建工具版本 | SDK 编译成功不等于服务端运行兼容 |
| UI | 页面、导航、组件、页面参数 | 页面注册了但导航指向旧页面 |
| 服务端 | 函数、HTTP 路由、认证上下文、日志 | 页面存在但请求进不了函数 |
| 配置 | 服务地址、逻辑工作区、Secret、成员映射 | 值仍指向云端旧实例 |
| 运行 | API 返回、动作结果、回读与页面刷新 | HTTP 成功但业务状态没有变化 |

原 App 包的 SDK/client SDK/UI 均固定 `2.41.0`，本地 server 为 `2.40.0`，App 声明 Node `>=24.5.0`。这是当时测试组合，不是通用兼容矩阵。新扩展选版本后重做类型检查、构建、函数和 UI 验收。

App 自己定义的 universalIdentifier 应在同一 App 演进时稳定；目标工作区成员、字段 UUID 与安装记录 ID 则需在目标重新解析。这两种标识不能一起“全部随机重建”，也不能一起“全部照抄”。

## 计划、应用与恢复

历史项目用带明确 remote 的 `plan --no-delete` 检查新增/修改，再 `apply --no-delete`。执行前读目标版本 CLI 帮助，保证参数可用并核对目标工作区。

官方当前同步文档仍提供 plan 和 no-delete，并说明部分导出不能覆盖所有 App 资源。接管不完整源码时先预览、保护未声明资源，不直接用删除式同步。[官方 App 同步与恢复文档](https://docs.twenty.com/developers/extend/apps/operations/sync-and-recovery)

`--no-delete` 只防删除，不保证所有修改无害；仍检查字段类型、关系、函数与变量变更。不要为修复一个元数据冲突直接卸载整个 App 或重置实例。多次同步按顺序执行，避免同一工作区交错迁移。

原仓库 App 标记为 private/UNLICENSED，且含公司绑定配置。按项目所有者要求，CRA 已在 chat-signal 资产中纳入去除实例绑定的客户版源码，保留私有分发属性；应用 API 和业务规则不直接兼容作者旧后台，按客户环境适配并验收。

## 凭据与身份

- 使用目标实例支持的 API Key/OAuth/CLI 登录；工具已安装、登录成功和当前会话能调用是三件事。先做只读实例核验。
- Secret 在服务端变量或客户凭据存储中配置，前端不得打包外部 Token。运行记录保留配置是否齐全，不保留值。
- 本项目使用 `workspaceMemberId` 判断允许访问的成员；云端成员 ID 不能用于本地。它也不一定等于全局 user ID。
- 响应的逻辑 workspace 与配置比对，避免接口正确却读取另一个客户的资料。
- API Key、应用服务身份及人的业务权限用途不同。此处只讨论技术调用所需的最小访问能力，不展开首版已排除的业务权限体系。
- 不把 macOS 钥匙串服务名做成跨平台依赖；更不将原脚本从 APP_SECRET 构造令牌的方式教给客户执行。

## 云端配置切换不等于业务实体重绑定

原项目新逻辑工作区只复制规则、分析设置和渠道配置；没有复制客户、商机、审批历史、旧 Outbox 或旧实体映射。因为云端 Twenty UUID 并不代表本地同一个记录。

目标实体先建立或识别，再保存新的映射；校验同一受管对象不能静默改绑、一个目标记录不能被重复绑定。切换工作区还需检查 webhook 路由、各 Worker 设置、App 变量和内部 API 地址，单改网页地址不够。

## 可靠写入的项目经验

这些能力来自项目自建适配器/数据库，不是 Twenty 原生工作流自动拥有的保证。

| 机制 | 解决什么 | 不能替代什么 |
|---|---|---|
| 固定外部 UUID/业务幂等键 | 响应丢失后重试不重复创建 | 不同业务误用同一个键的冲突检测 |
| 幂等键与请求内容同时比较 | 同键不同请求及时报错 | 客户业务上的重复识别 |
| `updatedAt` 条件更新 | 已被人工修改时阻止旧版本覆盖 | 未验证的“先读后写”原子性假设 |
| 持久 Outbox 与 attempt | 离线后可恢复、能追踪失败 | 目标接口自身事务保证 |
| 租约和 generation | 旧 worker 不能提交过期执行结果 | 外部副作用的去重 |
| 有界批次与重试 | 避免无限占用、重复冲击 | 一直失败时的人为处理 |

读取 HTTP 状态同时读取业务 payload；GraphQL 可能在 HTTP 200 内返回 `errors`。更新成功回读记录及版本，不能只写“网络请求成功”。

本项目先在早期本地版本探测，后在云端专用测试记录验证固定 UUID 和条件更新；又测试了本地离线恢复。必须注明各自版本与环境，不能由一套测试概括任何新版本。

## 待审核状态与实际执行分开

早期待审核中心只保存决定；后续 VPS 实现已承接匹配选择及重新归属后的执行，删除仍需人工处理。随包客户版将决定与执行结果分别显示，后台接通后逐项验证：待审、已批准、待执行、成功、冲突、失败及批准后人工操作，不由页面存在推断执行完成。

历史服务端覆盖未授权请求、过期摘要/相反决策冲突、同决策重放；有一份记录明确第二个真实非白名单成员的 UI 验收未完成。新客户若启用该能力，应补真实多会话验证，不能把服务端测试写成完整 UI 权限验收。

本页不连接 WhatsApp、不配置金蝶、不打开 AI 自动写入，也不启用任何外部服务。这些功能由相应 Skill 在其任务范围内设计、实施并验收，沿用 [基建交接约定](../08-ownership.md)。产品已确定的接入需求不因切换 Skill 而要求客户重新论证；具体执行仍依其已有授权和目标环境进行。
