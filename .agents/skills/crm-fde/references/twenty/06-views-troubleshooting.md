# 列表、看板、详情与白屏排查

适用：字段配置后界面不对、阶段顺序错、升级后页面无法初始化。主要证据：本项目 v2.40.0 迁移及旧筛选器修复记录。

## 字段存在，不等于客户看得见

配置完成后分别检查：字段是否启用、列表是否添加了列、详情布局是否显示、表单能否编辑、筛选器是否引用了正确字段、看板是否用正确阶段分组。API 能读出值不代表 UI 已完成配置。

列表建议围绕日常动作展示客户、负责人、星级、阶段、下次动作和到期时间；实际取舍按客户业务。隐藏列只改变展示，不能宣称数据访问权限因此隔离。

详情页应让客户找到相关联系人、商机、订单、任务和记录。关系字段配置正确后，仍需验证正常点击能打开关联记录，不能只核对后台 UUID。

## 看板顺序需要单独核对

原项目升级后，阶段 label 与看板 group position 分别存在问题：本地显示“备货”，且“配送”排在“成交”前。修复不只改 `stage.options`，还对齐对应视图分组的 `fieldValue` 与 position。

执行时：

1. 找到客户实际使用的看板；同对象可能有多个，不使用“第一个看板”默认值。
2. 检查分组字段、枚举 value、label、选项顺序和看板分组顺序。
3. 核对空值、赢单、输单、可选打样等是否按已确认流程展示。
4. 从正常列表导航进入看板，检查已有记录、移动阶段的行为与工作流副作用。
5. 重新加载或独立会话再看一次，排除旧缓存掩盖问题。

原审计脚本假定“恰有一个七组看板”，只是当时目标定位条件，不能成为新客户的限制。

## 历史白屏：自定义筛选器与官方版不兼容

旧定制镜像支持 `IS_BEFORE_DAYS_AGO`。改用官方 v2.40.0 后，遗留视图仍含该操作数，导致浏览器初始化白屏；`/healthz` 当时仍可正常。

有效排查顺序：

- 保留浏览器网络/控制台错误和触发页面，核对是否在初始化元数据时失败。
- 导出相关视图、过滤器、分组及字段关系，查找当前版本不认识的操作数。
- 确定旧定制来源，比较新旧功能；优先用当前支持的条件表达同一业务需求。
- 备份后只处理已经定位的受影响配置，验证其他视图未被改变。
- 必要重启后使用独立浏览器会话验证客户列表、联系人、商机页面。

原项目最终在明确范围内移除了一个旧视图，并对接口无法处理的孤立过滤器做了精确 ID 的内部软删除。这里保留的是故障证据，**不分发核心数据库修复命令，也不把删除视图当成默认解法**。目标实例若无法经支持入口修复，保留备份和证据，单独制定定点修复方案或寻求产品支持。

“超过 N 天未互动”的管理需求仍要保留：可用平台支持的过滤/计算方式，或已确认的定时任务表达；不能为消除错误把业务需求也删除。

## 常见现象的最短检查路径

| 现象 | 先检查 | 不应直接推断 |
|---|---|---|
| health 正常但白屏 | 初始化元数据、浏览器错误、旧视图操作数 | 数据库坏了、要重装 |
| 字段 API 有、列表没有 | 列配置、字段激活、当前视图 | 字段没有保存 |
| 阶段标签对、顺序错 | view groups 与 enum position | 只改枚举标签能解决 |
| 改显示设置后无变化 | 回读、目标字段、当前视图/布局 | HTTP 200 就生效 |
| 详情关联看起来丢了 | 关系实际值与详情组件分别核对 | 应重建客户或改绑关系 |
| 更换版本后过滤无效 | 操作数支持、类型与比较值 | 旧定制逻辑仍被官方支持 |

最终保留的 UI 验收证据应使用脱敏记录，不把真实客户截图放进可分发技能。
