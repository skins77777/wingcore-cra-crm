# 元数据盘点、跨实例映射与配置迁移

适用：把已确认业务蓝图落到 Twenty，或迁移另一工作区的配置。来源：字段盘点、云端契约、导出/审计/字段复制脚本和本地迁移记录。

## 先分清四类内容

| 类别 | 例子 | 处理方式 |
|---|---|---|
| 业务配置 | 字段、枚举、关系、视图、工作流 | 按确认蓝图比较和迁移 |
| 客户业务记录 | 公司、联系人、商机、订单、备注、任务 | 单独授权和数据迁移计划，不因迁配置顺便复制 |
| 系统配置/身份 | 成员、角色、系统关系、应用安装身份 | 读取作依赖分析；不全量覆盖到另一实例 |
| 凭据与运行态 | Secret、连接、队列、审批、外部实体映射 | 在目标环境重新配置或专门设计迁移，不能混入模板 |

本项目迁入云端业务元数据和 App，没有迁入云端测试客户或审批历史。这是一次“配置迁移”，不是完成了所有业务数据迁移。

## 导出不只是字段列表

必要资源按本次范围选择；缺一个依赖要明确标记，不能把失败请求写成空列表后认为“没有配置”。

- 对象和字段：内部单数/复数名、类型、选项、默认值、激活状态、设置、关系目标。
- 视图及子项：列、过滤器、过滤器组、排序、看板分组；只有 view 主记录不能恢复页面。
- 详情页布局及导航引用：配置了才纳入。
- 工作流、版本、触发器、步骤；Code 步骤引用的 Logic Function 源码和依赖另取。
- 成员和必要身份：用于负责人及引用映射，不能当成角色迁移授权。
- 业务数据：只有本轮包含数据迁移才导出，数据与配置分开存放。

原导出脚本处理了 REST 的数组包装和游标分页。复用方法时需检查每类资源的实际返回结构、页数、数量、下一页游标；出现重复游标或响应结构不认识就停止该资源导出，不能用第一页冒充全量。分页上限与批量写入上限也不能混为一谈。

每次导出保存：来源实例与版本、时间、资源名、响应状态、数量、页数/完整性、文件校验和。存入客户受保护档案，不提交包含成员信息、配置或源码密文的原始导出到通用 Skill。

## 建立稳定的语义键

对象先以实际内部名匹配，字段以 `对象内部单数名.字段内部名` 匹配；同时保留 REST 复数路由。比如概念上的商机、元数据 `opportunity`、REST `opportunities` 是三个不同层次。

```text
业务概念 → 对象内部名 → 源对象 ID → 目标对象 ID
业务字段 → 对象.字段内部名 → 源字段 ID → 目标字段 ID
枚举含义 → 内部 value → 目标选项 ID / label / position
关系       → 源/目标对象 + 关系方向 + 对应关系字段
```

显示名称只帮助核对，不是唯一匹配键。同名不同义不能自动合并；目标缺少对象、字段或关联时阻止依赖它的配置，先补齐映射。

跨实例需要重新解析的引用包括对象、字段、成员、关系字段、视图及分组、工作流版本和 Logic Function。不要仅替换顶层 UUID：步骤条件、模板变量、筛选器和嵌套 payload 中也可能有引用。修改应按已知结构进行，不对所有字符串盲目全文替换。

官方 API 随工作区 schema 生成。业务记录接口与元数据接口用途不同；先查看目标工作区生成的 API 文档，再构造 payload。[官方 API 文档](https://docs.twenty.com/developers/extend/api)

## 差异分类决定动作

| 差异 | 例子 | 建议 |
|---|---|---|
| 缺少已确认业务字段 | 赢单时间、订单统计金额 | 先核对含义/类型再补建 |
| 业务契约冲突 | 阶段 value 不同、关系目标错误 | 先做兼容映射及影响分析，不能仅改中文 |
| 显示差异 | 标准对象中英文名、默认列不同 | 按客户需要决定，不为零 diff 强改 |
| 版本增加的系统字段 | 邮件、日历关系 | 保留；不当成重复垃圾删除 |
| API 表示与实际约束不一致 | `isUnique` 与索引 | 按下面方法取证，不重复强建 |
| 接口成功但回读不变 | 标准对象 `readability` | 记录未生效或版本固定值，不伪造成功 |

原项目本地 554 字段，补 6 后为 560；这只是当时的完整性核对，不是每个客户必须创建 560 字段。新增包括两个对象各自的 `followUpSummary`、赢单时间和人民币统计金额等，是否用于新客户取决于蓝图。

## 两个容易误判的案例

**唯一约束不只看一个布尔值。** 原项目 `person.emails`、`company.domainName` 的 metadata REST 显示 `isUnique=false`，实际 PostgreSQL 已有 UNIQUE BTREE。重复创建触发 `INDEX_ALREADY_EXISTS`。自托管可通过有权限的只读索引检查辅助验证；Cloud 使用支持的接口、隔离重复值测试或厂商支持。不能据此宣称所有 `isUnique=false` 都是假，也不能通过直接改核心表“修正显示”。

**成功响应不保证保存。** 部分内置对象 `readability` 修改返回成功，回读仍是目标版本默认值。若不影响当前业务契约，标记差异并保留，不继续强制覆盖核心数据库。这也不代表成员权限已配置或已通过验收。

## 最小变更顺序

1. 导出源与目标，分别记录业务基线。
2. 生成新增、修改、保留、冲突、待核实清单；不默认生成删除清单。
3. 按依赖创建对象 → 基础字段 → 关系 → 枚举/设置 → 视图 → 工作流/函数。
4. 对复合字段、枚举选项更新核实是局部修改还是整组替换，保留仍在用的 ID 和选项。
5. 每批回读，对照语义键验证，不仅检查资源数量。
6. 重新导出做深度比较：忽略明确无业务意义的时间戳/安装身份差异，保留所有影响行为的差异。
7. 在 UI 检查字段、表单、排序，再运行代表性业务。未解决项写入实施记录。

需要接续时直接读取映射记录；不得重新猜测源/目标，也不要重复创建已通过验收的字段。
