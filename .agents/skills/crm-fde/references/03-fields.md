# 对象关系与字段字典

## 怎样使用本字典

本表供智能体备课与实施映射，不一次发给客户，也不是全部必建。先解释某个字段如何影响工作，再决定是否纳入首期；先检查目标 CRM 是否已有合适字段。无需展示的唯一标识、版本和任务去重信息可留在后台。

每个采用的字段至少明确：业务含义、类型/单位、未知如何表示、来源与更新者、用于哪些规则、修正影响。需要详细讲解时使用末尾教学卡。表中的“规则计算”指已验证的 CRM 内部确定性工作流，不指 AI 自动判断。

## 对象为什么分开

- **客户**：持续经营的合作对象，可以是企业或个人；保存长期合作信息。
- **联系人**：实际沟通的人，一家公司可有多位联系人；联系方式属于合适的人或公司。
- **商机**：一次独立采购机会；同一客户可以同时有多笔采购处于不同进度。
- **订单**：按已确认建单时点保存交易结果，用于统计；它不必在所有企业都等到赢单才建立。
- **任务**：下一步要做的动作，有负责人、日期与完成状态；任务完成不自动表示客户成交。

典型关系：客户 → 多个联系人/商机；商机 → 对应订单和多个任务；订单 → 客户；任务可同时关联客户和具体商机。联系人可能同时对应多个组织时按平台能力和真实业务处理，不因手机号相同就强行合并组织。

## A. 客户基础字段

| 字段 | 含义及用途 | 类型与空值 | 来源、更新及边界 |
|---|---|---|---|
| 客户名称 | 识别合作对象，显示在列表和单据关联处 | 文本；可用明确标注的临时称呼 | 人工录入/导入；名称相似不能作为唯一合并依据 |
| 客户类型 | 区分企业/个人，决定关联方式 | 枚举；未知待确认 | 业务员确认；不要给个人客户强建不存在的公司 |
| 联系人关联 | 知道应联系谁，人员变动仍保留客户历史 | 多记录关联；允许暂缺 | 选择现有或新建联系人；换人不覆盖其他人的信息 |
| 客户负责人 | 谁承担日常经营与待办 | 成员/人员关联；未分配独立表示 | 按归属规则赋值；负责人字段不等于权限隔离 |
| 客户来源 | 了解获客渠道，按来源复盘 | 受控选项；允许未知 | 人工选择/导入；区分首次来源与后续沟通渠道 |
| 国家/市场 | 辅助联系安排、市场分析 | 国家/地区字段或受控文本 | 人工核实；电话号码区号不必然等于销售市场 |
| 产品需求分类 | 快速了解感兴趣的产品 | 多选；未知为空 | 业务员选择字典；不要自动扩充混乱标签 |
| 客户备注 | 保存人工判断和关系背景 | 长文本；允许空 | 人工维护；避免把所有日期、金额和状态塞进备注 |
| 客户等级 | 分配维护资源 | 1–5 星；待了解独立 | 根据确认的评级规则计算，错误可纠正 |
| 月/周期采购潜力 | 表示可能的采购规模 | 非负数或范围，搭配单位与周期；未知空 | 人工录入明确依据；范围跨等级时需约定保守档或待确认，不能擅取上限 |
| 累计成交金额 | 在明确口径内完成的合作贡献 | 金额与币种/统一统计币种 | 订单汇总；资料未导全时标记覆盖范围 |
| 成交次数 | 独立计入统计的订单数 | 非负整数；历史不完整不能假装全量 | 订单汇总，分批收付款不重复计数 |
| 最近维护完成日 | 无活跃商机时计算下次维护 | 日期时间；从未维护为空 | 来源是维护任务完成；不能把编辑记录当完成维护 |
| 客户关系状态（可选） | 长期关系，如潜在、合作、复购 | 受控选项；定义逐项确认 | 可以由订单统计派生；老客户新询价不回退成新客户 |

客户列表首屏通常只需要名称、负责人、等级、关键关系信息和待办。是否显示“国家”“分类”等根据客户如何筛选工作决定。

## B. 联系人字段

| 字段 | 含义及用途 | 类型 | 来源与边界 |
|---|---|---|---|
| 姓名/称呼 | 找到实际沟通的人 | 文本 | 人工/导入；同名不自动合并 |
| 所属客户 | 把沟通人关联到合作对象 | 关联 | 公司变动要保留历史，不移动全部历史交易 |
| 职务/业务角色 | 知道对方负责采购、技术还是付款 | 文本/受控选项 | 已知才填，未知不推断决策权 |
| 电话/WhatsApp 号码 | 联系与识别 | 电话，保留国家代码 | 格式标准化；共享号码/换号需核实，不以号码一项覆盖全部关系 |
| 邮箱 | 联系、发文件 | 邮箱或多值字段 | 避免同人多邮箱被建成多人；企业公共邮箱可能多人共用 |
| 主要联系人标记（可选） | 首次联系时优先找谁 | 布尔或客户侧单关联 | 多联系人时说明主联系人规则；不删除其他联系人 |

地址按需要区分公司地址、账单地址、收货地址及收货联系人。只涉及单次采购的收货地址更适合放在该商机/订单，不能覆盖客户全部地址。

## C. 商机字段

| 字段 | 含义及用途 | 类型与空值 | 来源、更新及边界 |
|---|---|---|---|
| 商机名称/编号 | 区分同一客户的不同采购 | 文本/系统编号 | 使用可辨识名称；后台保留稳定 ID |
| 客户/联系人 | 明确采购属于谁、与谁沟通 | 关联 | 负责人手工确认；别只靠备注写人名 |
| 商机负责人 | 谁推进本次采购和处理任务 | 人员关联 | 可默认客户负责人；特殊协作规则另行明确 |
| 当前阶段 | 当前需要采取哪类动作 | 受控枚举 | 成立条件可由可靠字段确定时由已验证工作流更新，否则按企业规则人工维护或待事实接入；合法迁移和下游动作由规则校验 |
| 阶段进入时间 | 衡量本阶段停留时间 | 日期时间 | 真正阶段变更时记录；编辑备注、重复保存同阶段不重置 |
| 产品/规格 | 这笔采购需要什么 | 文本、产品关联或行项目 | 人工录入；不同产品不要揉成不可追踪的一项 |
| 需求数量/单位 | 本次询价或需求口径 | 数字/范围 + 单位 | 允许早期不确定；区别于客户月采购潜力和最终订单数量 |
| 交货地点 | 本次采购交到哪里 | 文本/地址关联 | 属于本次采购；不等于公司注册地址 |
| 期望交期 | 客户希望何时收到/交付 | 日期或范围，并保留“期望”性质 | 后续约定交期可另存；不能把意向变成承诺 |
| 正式报价文件 | 找到本次有效报价 | 附件/链接 | 人工上传关联；本版不自动读取 PDF 内容 |
| 报价版本/有效状态 | 防止旧报价覆盖新结果 | 文本编号 + 当前/作废等状态 | 保留历史和客户接受的版本；不用文件修改时间替代业务版本 |
| 报价发送时间 | 触发报价后跟进 | 日期时间 | 人工记录已发送；上传草稿不等于已发送 |
| 报价金额/币种 | 本版报价提出的价格 | 精确金额 + 币种 | 人工录入；后续最终成交价不同也保留原口径 |
| 约定定金金额 | 判定是否达到这笔订单的收款门槛 | 金额 + 币种 | 单独约定时每单填写；不能默认任何到账都足够 |
| 定金到账确认 | 是否经核实达到约定门槛 | 状态 + 确认人/时间 | 首版人工核实后确认；客户截图不自动等同核实 |
| 尾款收齐确认 | 是否达到公司约定的收款完成条件 | 状态 + 确认人/时间 | 人工核实；有退款、折让先明确应收基数 |
| 最终成交金额/币种 | 此笔最终约定的统计金额 | 精确金额 + 币种 | 人工确认；不能用最后一笔收款金额替代全单金额 |
| 约定联系日期 | 尊重已明确的后续联系安排 | 日期时间；未约定为空 | 人工录入；如何替代已生成任务按规则处理 |
| 下一步动作 | 推进这笔采购的具体行动 | 简短文本 | 人工维护；配套任务截止日期用结构化字段 |
| 跟进备注 | 当前进展和背景 | 长文本 | 首版人工记录；不配置 WhatsApp 自动小结 |
| 输单主要原因（默认必建） | 统一归类，支持输单原因分析 | 固定选项单选；转输单时必有合法值；可配补充说明 | 人工/已授权工作流或模型依据事实填写；至少提供客户不回复、其他；停滞不等于不回复，不猜商业原因 |
| 打样状态（可选） | 追踪按需样品环节 | 独立状态/子流程/任务 | 平台支持什么就采用什么；不强制压成必经阶段 |

输单原因的选项与证据口径见 [输单规则](05-process.md)。创建或复用平台单选字段，确认稳定选项与实际映射；列表可按原因筛选和汇总。不要只写说明而遗漏字段配置，其他类保留已知事实说明以便日后细分。

不是所有商机都应把上表每项设成创建时必填。按阶段设置“到这个节点才需要”的条件，让早期机会能先记录。

## D. 订单字段

| 字段 | 含义及用途 | 类型 | 来源与边界 |
|---|---|---|---|
| 订单编号 | 唯一识别交易记录 | 稳定编号 | CRM 生成或业务编号；不能只有显示名称 |
| 来源商机 | 保证交易结果可追溯、避免重复建单 | 唯一关联/幂等标识 | 按已选一商机一单规则约束；拆单业务另定，不暗自套用 |
| 客户关联 | 将贡献计到正确客户 | 关联 | 从已确认商机带入；转移客户属于显式更正 |
| 订单日期/计入统计时间 | 确定哪个统计期间的贡献 | 日期时间 | 根据建单/计入规则产生，不混用开票日期 |
| 订单金额/币种 | 当前有效订单贡献 | 精确金额 + 币种 | 来源最终确认金额；金额修正同步统计 |
| 订单数量/单位或明细（可选） | 保留最终交易内容 | 数值 + 单位/多行 | 不同口径分开，不以总件数代替多种产品明细 |
| 是否计入统计/有效状态 | 取消或冲正后可解释统计变化 | 状态/布尔 | 优先可追溯调整，不通过硬删抹去依据 |
| 原因/修订记录 | 解释金额或状态为什么变化 | 事件记录/说明 | 有前后值、时间和操作者；不把草稿变化当正式贡献 |

税、运费、退款、不同币种的策略见订单教材。首版可采用一个已明确的统计口径，不自动搭建完整财务系统。

## E. 任务字段

| 字段 | 含义及用途 | 类型 | 来源与边界 |
|---|---|---|---|
| 标题/动作 | 业务员具体要做什么 | 短文本 | “了解报价反馈”优于“跟进一下” |
| 类型 | 区分报价跟进、停滞复核、关系维护 | 枚举 | 决定去重和周期，不靠标题关键词猜 |
| 客户/商机关联 | 正确归属，打开任务能看上下文 | 关联 | 商机任务精确关联采购；维护任务可以仅关联客户 |
| 负责人 | 谁执行 | 人员关联 | 从商机/客户规则分配；未分配必须显式可见 |
| 截止时间/提醒时间 | 决定何时出现在待办 | 日期时间 + 公司时区 | 业务规则计算；不要从长文本日期临时猜 |
| 状态 | 未完成、完成、取消/不适用等 | 枚举 | 首版由人完成，系统按已确认规则停止不再适用任务 |
| 完成时间 | 算下一轮周期 | 日期时间 | 手动完成触发；取消不当成有效维护完成 |
| 报价轮次/跟进次数 | 控制这轮最多几次 | 后台标识/计数 | 重试不多算；任务创建和实际完成的次数需定义 |
| 去重标识 | 防止同一动作反复创建 | 后台稳定键 | 包含目标、任务类型、对应阶段/报价轮次和规则版本策略 |
| 创建依据 | 解释为什么出现 | 规则版本/来源事件引用 | 保留可追溯依据，不必占客户列表空间 |

“后台标识”是实现契约，可用目标 CRM 原生机制实现，不要求必须新增这些名字的用户字段。

## 字段教学卡的写法

例：“阶段进入时间”教学卡：

- 为什么：避免一直闲聊却误以为销售在推进。
- 含义：真正进入当前阶段的时间，不是最近编辑时间。
- 例子：10 日进入报价，12 日补备注，仍从 10 日算停滞。
- 来源：阶段变更动作；由 CRM 规则记录。
- 作用：超过公司确认的期限产生复核任务。
- 异常：历史数据没有进入时间，标为未知，不能立刻把全部旧机会判逾期。
- 以后怎么改：“把停滞复核从 30 天改成 45 天，先展示受影响的商机。”

使用 [字段模板](../assets/fields.md) 保存最终合同。至少一个正例、一个边界例帮助检查含义；不要为了文档齐全给每个无争议名称写长篇。

## 字段教学发生在做决定的时候

这份字典是备课材料，但面向客户的解释不是可省略的。采用一个新的关键业务字段时，用一两句讲清：它记录什么、解决哪个具体问题、谁填或从哪里算。对应概念此前已讲过就复用，不逐字段背整张卡。

例如客户确定 PDF 报价后：“保存报价文件、版本和发送时间；以后能找回客户接受的版本，发送时间用于安排跟进。”确定累计成交额时说明它来自有效订单，而不是预算或定金；确定输单原因时说明汇总可以帮助经营判断。

模块末尾把采用字段写入字段字典并核对关系，不把全部技术字段都展示给客户，不要求客户自己列字段。阶段进入时间、去重键等可由智能体设计；客户只需理解它们对计时、重复任务的影响。
